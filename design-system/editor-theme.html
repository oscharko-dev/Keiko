Guidelines · 09 · Editor

Editor theme tokens

The governed colour set a Monaco-grade code surface needs — syntax palette, editor chrome, diff, diagnostics and ghost text — in dark, light and high-contrast. It extends the base palette rather than forking it: roughly two-thirds of editor chrome reuses --bg / --fg / --danger / --warn / --info; the net-new work is the syntax hues and the editor-specific chrome. Engineering maps these straight onto Monaco colors and tokenColors — no ad-hoc colours downstream.

07 — DIVERGENCE & RATIONALE

Why the editor diverges from the UI palette

Multi-hue syntaxThe app shell is intentionally monochrome with a single green accent. Code is the exception: distinguishing eleven token types at a glance requires hue variety. This is a deliberate, documented divergence — confined to the code well, never leaking into chrome.
Reuse over invention~60–70% of chrome reuses base tokens: gutter & guides from the neutral ramp, diagnostics straight from --danger/--warn/--info, tabs/status from --surface/--fg. Only the syntax hues, diff tints, find/selection and ghost text are net-new.
Editor well ≠ cardThe code background uses the darkest/lightest inset tone (not --card) so syntax hues sit on a calm, low-chroma field — the condition under which the contrast figures were measured.
Green stays structuralBrand green is reserved for selection, the active-tab marker, bracket match and the suggest highlight — structure and state — never for a syntax token, so "Keiko green" keeps one meaning.
High-contrast targetsThe HC variant lifts every syntax hue to ≥ 7:1 on a near-pure code well and is exposed both via prefers-contrast: more and an explicit [data-hc="more"] hook for a user-facing toggle.
Deliverable
Tokens live in keiko-editor-tokens.css, alongside the base keiko-tokens.css. They extend the source of truth and are ready for the Monaco theme work in #1193 to map without inventing colours.
