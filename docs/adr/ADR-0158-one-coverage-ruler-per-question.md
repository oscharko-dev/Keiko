# ADR-0158 — One coverage ruler per question

- Status: Accepted
- Amends: [ADR-0157](ADR-0157-sharded-coverage-evidence-and-cached-provisioning.md) (D1, the
  mechanism by which a shard is prevented from judging; every other ADR-0157 decision stands)
- Extends: [ADR-0156](ADR-0156-measurement-and-verdict-separation.md) (D1, one verdict in one
  place, from the separation of producer and judge to the elimination of duplicate judges)

## Context

Ten coverage rulers had overlapping jurisdictions, and the overlap was neither documented nor
deliberate. It had accreted, one defensible addition at a time, until no single artifact answered
"what is the floor for this file, and who enforces it".

Four facts were measured on `dev` at 4d4c0838, not estimated.

The full jsdom keiko-ui coverage suite executed **twice per pull request**. Once in `coverage-ui`,
whose LCOV and summary are uploaded, downloaded by `coverage-sonar`, and read by every ratchet and
by SonarCloud. Once more in the `ui` job, on a different runner, followed by a ratchet reading that
runner's local summary — a verdict on evidence no other step ever saw, and the second-longest step
in a job on nobody's critical path. Removing it removes a full jsdom suite from every pull request
and changes no verdict, because keiko-ui's lines coverage was judged by three floors and the
strictest of them lives elsewhere: an 85 ratchet in `check:coverage`, the same 85 in the `ui` job's
`check:coverage:ui`, and the 88-strict release target in `check:coverage:release-targets`. 88
strictly dominates 85 on the same metric of the same package.

`scripts/check-package-coverage.mjs` ran **six times per run across five npm scripts** — the file
floors and lines ratchet, two chained strict release targets, then statements, branches and
functions — each re-parsing the same two `coverage-summary.json` files, although one run of the
script already computes all four metrics. Five of the six invocations existed only because the
command line could express one metric at a time.

Per-file floors lived in **two engines with different storage and different noise policy**.
`fileFloors` in `docs/qa/package-coverage-baseline.json` governed 46 files, lines only, ratcheted
against a recorded measurement, with 0.5 percentage points of headroom. The vitest
`coverage.thresholds` block in `vitest.coverage.packages.config.ts` governed 10 gate scripts,
absolutely, across all four metrics, with no headroom at all. One failed a test run; the other
failed a downstream check. Nothing named which applied to a given file, and no engine could see
what the other governed.

The constitutional 85 was written down twice: `target` in the baseline and
`KEIKO_REPOSITORY_GATE_CONTRACT.newCodeCoverageMinimum` in `scripts/sonar-quality-gate-contract.mjs`.
Two copies that agree today are one edit away from a repository whose local ratchet and whose
required SonarCloud condition disagree about the same number.

Alongside these, two orphans: `docs/qa/package-coverage-report.md`, generated by nothing (the
`--markdown` flag that would produce it is passed nowhere), and `check:coverage:strict` and
`check:coverage:branches:strict`, wired into no workflow and no local suite.

The charter for removing any of this is narrow, and it is the reason this record exists rather than
a cleanup commit: **no numeric value may decrease and no tolerance may widen anywhere.** A duplicate
*evaluation* may be removed only where a strictly dominating check remains and continues to execute
in a required pull-request context.

## Decision

**D1 — One per-file floor engine, one storage location.** `fileFloors` in
`docs/qa/package-coverage-baseline.json` is the single per-file floor store, and
`scripts/check-package-coverage.mjs` is the single engine that reads it. The vitest
`coverage.thresholds` block is retired and its ten gate-script floors are migrated into the store
unchanged (branches 85, functions 90, lines 90, statements 90).

The store is chosen over the vitest block because it is the only one of the two that can express
what has to be expressed. Five of the 46 ratcheted entries are keiko-ui files, which
`vitest.coverage.packages.config.ts` excludes entirely and which the keiko-ui configuration does not
threshold; a floor for them cannot live in a vitest block at all. The store also already fails
closed on a governed file that vanished from the summary, which a vitest threshold does not.

`schemaVersion` moves 1 → 2. Schema 1 stored a bare lines number per entry at an implicit fixed
tolerance. Schema 2 stores an object per entry carrying `governance`, an explicit `tolerance`, and a
floor for each governed metric. A schema-1 entry encountered under schema 2 is rejected by name
rather than silently half-enforced, which is what the version bump is for: the migration has no
valid intermediate state.

`governance` is the per-entry policy, and it is load-bearing on the regeneration path.
`"ratcheted"` entries are re-derived from measurement by `--file-floor-threshold` and allow 0.5
points of platform noise. `"absolute"` entries encode a policy rather than a measurement, allow
none, and are carried through regeneration verbatim. Without that distinction, regenerating the
baseline would delete all ten gate-script floors on the first run, because every one of them sits
far above the ratchet threshold that decides which files get recorded.

Percentages are compared **unrounded**. Rounding the current measurement to two decimals before
comparing it against a zero-tolerance floor would let 89.996% satisfy a floor of 90 — a tolerance of
0.005 points introduced by the comparison itself, which is exactly what "no tolerance widens" forbids.
The package-level ratchet's comparison basis is deliberately left unchanged; only the per-file engine
tightens.

**D2 — One evaluation pass.** `check:coverage:quality` is a single invocation of
`scripts/check-package-coverage.mjs` that parses the summaries once and evaluates, in that one pass:
the package ratchet for lines, statements, branches and functions (`--all-metrics`); the per-file
floors (`--enforce-file-floors`); and the strict release lines targets (`--release-target
keiko-ui=88 --release-target keiko-cli=87`). Every floor value and every ratchet, strictness and
epsilon semantic is preserved exactly; what changes is the number of processes that compute them.

The release targets are inside this pass rather than beside it because D4 depends on them: they are
the checks whose continued execution makes the removal of the dominated 85 evaluations valid. A
release target whose package was not measured at all fails closed rather than reading as met.

**D3 — One constant.** `KEIKO_REPOSITORY_GATE_CONTRACT.newCodeCoverageMinimum` is the single
definition of the constitutional 85. `scripts/check-package-coverage.mjs` imports it as its default
target, the generated baseline records it rather than choosing it, and a baseline whose `target`
disagrees with it fails the gate closed. The local ratchet and the required SonarCloud `new_coverage`
condition are now the same number by construction.

**D4 — One execution per coverage suite per pull request, removed only by dominance.** The `ui`
job's `npm run test:coverage:ui` and `npm run check:coverage:ui` steps are removed. The suite is
measured once, by `coverage-ui`, and judged once, by `coverage-sonar`.

The removed ratchet was keiko-ui lines at floor 85. The 88-strict release target binds the same
metric of the same package more strictly and continues to execute on every pull request inside
`check:coverage:quality`, in the required `Coverage and SonarCloud` context — so no keiko-ui lines
regression that the removed check would have caught can pass the surviving one. The identical
argument applies to keiko-cli at 87 against 85. The ratchet remains authoritative for statements,
branches and functions on both packages, and for every metric of every other package. This is the
only removal argument this record admits: a dominated evaluation, with its dominator still executing
in a required context.

**D5 — With no vitest configuration judging, a shard cannot judge.** ADR-0157 D1 kept
`vitest.coverage.packages.shard.config.ts` — the judging configuration with `coverage.thresholds`
removed — because vitest evaluates thresholds against whatever a run produced, so a shard measuring
a third of the suite would judge it against the whole suite's floors. D1 above removes the last
`coverage.thresholds` block in the repository, which makes that derived configuration a no-op
transform of its own source, so it is deleted and the shards run against the one package coverage
configuration.

ADR-0157 D1's property is unchanged and is now stronger: it was maintained by a second configuration
file that a hand-written copy could have drifted from, and it is now structural — there is no
threshold anywhere for a shard to evaluate. `scripts/__tests__/vitest-config-parity.test.mjs` pins
that structurally, asserting that *no* vitest configuration declares `coverage.thresholds`, and the
ten floors' numeric values are pinned at their new home against the committed baseline. ADR-0157 D2
(merge before evaluate), D3 (fail closed on any non-success shard), D4 and D5 are untouched.

**D6 — Dead scaffolding is deleted, not documented.** `docs/qa/package-coverage-report.md` and the
`--markdown` flag that would have generated it, and the unwired `check:coverage:strict` and
`check:coverage:branches:strict` scripts, are removed (AGENTS.md §6). The same table the flag wrote
is still printed to stdout on every gate run, where it is actually read.

## Consequences

Every pull request runs one fewer full jsdom coverage suite and one instead of six evaluation
processes. No floor moved: the floor-mapping proof on the adopting pull request lists all 86
governed (file, metric) pairs with old value → new value and old tolerance → new tolerance, and no
row decreases a value or widens a tolerance. Coverage for the ten gate scripts is enforced across all
four metrics, as before, at the same numbers, from a store that can also express the 46 ratcheted
files the vitest block never could.

One enforcement point moves between steps of the same job. A gate-script regression used to fail
`npm run test:coverage:packages:merge`; it now fails `npm run check:coverage:quality`, the next step
in `coverage-sonar`. Both are in the same required context and neither can be reached without the
other running.

The `ui` job no longer produces a coverage summary at all, which makes the `Download keiko-ui
coverage evidence` step in `coverage-sonar` the only path by which keiko-ui's measurement reaches the
ratchet, the strict 88 target and SonarCloud. `scripts/__tests__/dev-quality-workflows.test.mjs`
pins that download, and the strict target fails closed when the package is unmeasured, so a dropped
artifact reads as a failure rather than as coverage met.

`scripts/check-new-code-coverage.mjs` — the local mirror of SonarCloud's `new_coverage` condition —
listed `coverage/ui/lcov.info`, a path no configuration writes, and omitted the real
`packages/keiko-ui/coverage/lcov.info`. It therefore measured zero keiko-ui new code while reporting
a verdict. `docs/qa/coverage-truth-model.md` documents this script and the required SonarCloud gate
as one ruler with two mirrors, and a mirror that cannot see a third of the LCOV does not answer the
question the document says it answers, so the path list is corrected here.

Rollback is a single revert of the adopting commit: it restores both engines, the duplicate
execution, the shard configuration and the six invocations together. The `schemaVersion` bump is what
makes a partial rollback fail closed instead of enforcing half the floors — a schema-1 baseline
against the schema-2 engine, or the reverse, is rejected by name rather than silently accepted.

`docs/qa/coverage-truth-model.md` records the resulting map: question → single measuring artifact →
single enforcement point → threshold → tolerance. It is the artifact this record exists to make
possible, and the thing whose absence let ten rulers accrete.
