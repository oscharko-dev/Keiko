## 1. Executive summary

The Coding Workbench runs two separate agent loops. The engine a user drives today is a pinned third-party coding-agent child process (`OPENCODE_PINNED_VERSION = "1.17.17"`, `packages/keiko-server/src/coding-runtime/opencodeToolSchemas.ts:9`), called the bridge engine throughout. It owns message history, tool choice, and turn-ending decisions inside a governed launch profile; Keiko owns everything touching a credential, a real file, or the outside world through a re-authorized, per-call authority port. A second, Keiko-owned loop, `keiko-harness`, already runs in production — but only for a narrow, read-only, single-tool sub-agent and for two of its five task types (`explain-plan`, `verify`). It has no import edge to the context-engineering package that would let it compact a long session, no plan artifact beyond a static per-task-type string, no tool-call streaming, and it ends a run outright on any tool failure instead of feeding the failure back to the model.

What is real and wired: a nine-tool, digest-pinned model surface; live per-call re-authorization against the current envelope; a fail-closed sandbox and workspace-boundary chain reused by every tool; a body-free evidence/diagnostics layer with structured redaction tokens; a three-mode, 48-cell, monotonic authority matrix that can never get stricter as mode rises nor laxer as it falls; and a content-bearing, authenticated live-activity channel for text, plan, and questions.

What is declared-only: a per-run `commandPolicy` shape hardcoded to deny every command regardless of mode; three counters (`toolCallCount`, `modelRequestCount`, `patchByteCount`) always written zero; a `StreamDelta.toolCallDelta` wire type no adapter emits; an unmounted autonomous-delivery route group on the wrong client-authored trust model; and a live activity feed that strips exactly the arguments, command lines, and diffs human-visibility requires it to show.

The ten largest gaps against the market baseline (Section 7): no plan-mode approval gate before the first edit; no model-callable governed shell; no fine-grained per-tool/command permission-rule engine; no repository content search (filename/path matching only); no token/cost/context meter; no reachable per-run model picker; no tool-call streaming; no durable session persistence/resume/history; no MCP client; and no per-repository project-instructions loading into the agent's context — ironic, since Keiko's own contributor process depends on it.

Keiko already exceeds the baseline in four places no reference product documents: a closed, pattern-validated evidence contract body-free by construction; a SHA-256-hash-bound, TOCTOU-safe patch tool; a quarantined research-fetch path that neutralizes injection markers before the model sees fetched content; and a fail-closed, monotonic three-mode matrix backed by a pinned regression test.

Conclusion the roadmap builds from: every gap above has a landing spot already built one layer down — a widened envelope field, an existing gateway, an existing port — so parity is reachable by extending the blocks in Section 3 inside the current authority envelope (the S1–S10 spine), not by adding a new trust boundary, policy engine, or second implementation of anything Keiko already owns.

## 2. The production engine

Scope: `packages/keiko-server/src/coding-runtime/` and its immediate collaborators (`coding-sidecar-gateway.ts`, `coding-app-session/`, `coding-codex-subscription.ts`, `packages/keiko-model-gateway/src/model-selection.ts`, `packages/keiko-contracts/src/coding-workbench*`).

### 2.1 Process and trust model

Two processes share one trust boundary. The bridge engine child owns the agentic loop — message history, next tool choice, when a turn ends — driven by the governed system prompt baked into its launch config (`opencodeLaunchProfile.ts:27`). The BFF (`keiko-server`) owns everything touching a credential or the outside world: it mints the run's Authority Envelope and two short-lived, run-scoped bearer capabilities (`runtimeAuthorityService.ts:586-605`), spawns/supervises the child, runs a private per-run tool-facade HTTP server only the child can reach, and is the sole path to real model providers and workspace files. The child never sees a provider API key — only an opaque, expiring capability good only against Keiko's own loopback endpoints.

```
UI            BFF (keiko-server)                       Bridge engine child   keiko-model-gateway
 | POST runtime/runs -->| mint envelope+capabilities;           |                  |
 |                       | spawn the bridge engine, port 0------>|                  |
 |                       | start-turn(taskIntent) --------------->|                  |
 |                       |<--- POST 127.0.0.1:{port}/tool --------| picks a tool     |
 |                       | Ipc->Facade->AuthorityPort (re-checks |                  |
 |                       | the LIVE envelope) -> port -- result ->|                  |
 |                       |                                        |--POST /coding--->| chat.completions
 |                       | validate digest-pinned 9-tool schema,  |  -sidecar/gateway|
 |                       | authenticate, forward ---------------------------------->|  (configured provider)
 |                       |<-----------------------------------------------------------|
 |<- content-free SSE ---|                                                            |
 |<- authenticated safe-activity stream -|                                            |
```

Two checks stop the child widening its own authority: every tool call is re-authorized against the **live** envelope, not a cached launch-time decision (`codingToolAuthorityPort.ts:71-99`, `revalidateCapabilityForMutation`); and every chat-completions call is checked against a SHA-256 digest of the exact nine-tool JSON-schema set before forwarding to a real provider (`opencodeToolSchemas.ts:367-379`, `coding-sidecar-gateway.ts:1401`) — a mismatched tool surface is refused via `forbiddenGatewayRequest()`.

### 2.2 Launch profile and configuration

- **Binary pin**: `OPENCODE_PINNED_VERSION = "1.17.17"` (`opencodeToolSchemas.ts:9`). **Argv**: `serve --hostname 127.0.0.1 --port 0 --no-mdns` (`opencodeLaunchProfile.ts:61`) — loopback, ephemeral port, no discovery broadcast.
- **Isolation**: home/profile, config, state, and temp-directory env vars redirect under a private per-run `stateRoot`; project-level config loading is disabled (`opencodeLaunchProfile.ts:62-74`); a fresh 32-byte server-password secret is generated per run, present only in the child's environment, never in the config file.
- **Config generation**: `createFixedOpenCodeConfig()` (`opencodeLaunchProfile.ts:79-129`) emits a fixed JSON document — autoupdate/local snapshotting off; one provider shimmed at `{env:KEIKO_MODEL_GATEWAY_URL}` with a bearer capability header; one model alias `coding` declaring `limit:{context:32_768, output:4_096}`; a 30-minute provider chunk timeout, since the outer BFF turn ceiling, not the child's own short default, is the real deadline.
- **Tool/permission maps**: every bridge-engine built-in tool (`opencodeToolSchemas.ts:312-328`) is denied; the nine model-visible tools (2.3) are allowed; a synthetic catch-all permission `keiko_governed_action` is `"ask"` (`opencodeLaunchProfile.ts:118-127`). A generated plugin (`opencodeRuntimeAdapter.ts:922-940`, materialized per run at `opencodeRuntimeComposition.ts:473`) classifies each edit/verification call's risk and raises it through the bridge engine's own permission-ask protocol; the BFF reads that event (`opencodeProtocol.ts:281-293`) and projects it into `awaiting-approval` (`codingRuntimeOrchestrator.ts:285`).
- **System prompt**: `OPENCODE_GOVERNED_SYSTEM_PROMPT` (`opencodeLaunchProfile.ts:27`) replaces the default prompt outright — a comment notes the default taught bash/grep/glob workflows that live models followed into tool-free text turns (#2680). It states the session has no shell/direct file access, names every disallowed built-in, and lays out a five-step workflow (plan via `todowrite` → discover → read → edit → verify) plus a `question` tool reserved for operator-owned decisions.

### 2.4 Model path

Every model call leaves the child as `POST /api/coding-sidecar/gateway/chat/completions` (`routes.ts:479-480`), handled by `handleCodingSidecarGatewayChatCompletions` (`coding-sidecar-gateway.ts:1378`), which authenticates the capability, validates the tool-schema digest, reserves a prompt-token budget, and forwards through `keiko-model-gateway`. A kill switch, `KEIKO_CODING_SIDECAR_DISABLED` (`coding-sidecar-gateway.ts:35,436-438`), disables the whole sidecar. Model selection is not "cheapest tool-calling chat model": `selectCodingSafeSidecarCapability` (`model-selection.ts:232-243`) picks the lowest-`costClass` capability that is `kind:"chat"`, `toolCalling`, `workflowEligible`, **and** carries a coding-preferred use case (lines 210-230); the same resolver fails closed for the retired subscription-lane source (Section 6).

The child sees only the redacted tool results in 2.3 plus its own history — never real provider identity, endpoint, or credentials: `KEIKO_MODEL_GATEWAY_CAPABILITY` is a short-lived, run-scoped, audience-scoped opaque token minted by `RuntimeCapabilityStore.issue` (`runtimeAuthorityService.ts:586-616`), never the provider API key held inside `keiko-model-gateway`. The model alias caps context at 32,768 and output at 4,096 tokens (`opencodeLaunchProfile.ts:103-104`); a nightly real-binary lane asserts the live child receives exactly this pair and the gateway enforces `maxOutputTokens:4096` at the provider boundary (`docs/coding-runtime/milestone-1-real-binary-validation.md:62-70`).

Usage reporting: nothing per-run is aggregated for display today — the persisted lifecycle row's `modelRequestCount`/`toolCallCount`/`patchByteCount` are permanently `0` (2.7). A separate in-memory evidence aggregator counts `tool-call`/`model-request` observations (`productionOpenCodeBackend.ts:453-476`), but only as an integer in the terminal manifest — never tokens, live, or cost.

### 2.5 Run lifecycle

Thirteen states, defined once (`coding-workbench-runtime.ts:44-73`): `unavailable, idle, starting, ready, running, paused, awaiting-approval, stopping, succeeded, failed, cancelled, taken-over, recovery-required`. `codingRuntimeOrchestrator.ts` (1,223 lines) is the single state-machine owner; `CodingRuntimeManagerImpl` in `codingRuntimeManager.ts` (3,004 lines) owns process spawn/supervision underneath it. **One active run per BFF** is enforced in `startFresh` (`codingRuntimeOrchestrator.ts:787-788`): `if (!parsed.ok || this.activeRunId) return this.fail(...)`, reloaded from the durable snapshot store on construction (line 173) so the constraint survives a restart — the exact constraint parallel Code tasks must lift.

Only a `running` run may pause; a paused run still accepts inline answer/reject and stop, never a widening mode change (lines 249-253). Takeover/stop share one code path (`end(kind:"stop"|"takeover")`, lines 941-1042). Follow-up (`submitFollowUp`, line 233; `codingRuntimeRoutes.ts:373-380`) admits a drafted message only while `running`, bound to the current revision — no hidden prompt queue is possible. Any BFF-side exception mid stop/takeover forces `recovery-required` rather than trusting settlement (lines 1018-1024). Every lifecycle-mutating route (start, approve, stop, takeover, retry, recovery-ack, pause, resume, follow-up, research-revoke) funnels through one authority choke point, `mutation()` (`codingRuntimeRoutes.ts:170`, guard at lines 139-155), requiring the launcher-attested app-session cookie (ADR-0141 D2).

**Budgets**: the Authority Envelope minted per run (`productionRuntimeWorkspaceAuthority.ts:79-127`) carries `maxRuntimeMs` = 30 minutes (`RUNTIME_TTL_MS`, line 22), `maxToolCalls:256`, `maxPromptTokens:200_000`, `maxPatchBytes:262_144` (lines 123-126). The same envelope already declares a `commandPolicy` shape — `{mode:"deny", allow:[], deny:[], maxCommandTimeoutMs:1, requirePerCommandApproval:true}` (lines 112-118) — fully denied today, with the allow/deny/per-command-approval fields a governed shell tool would need.

### 2.7 Persistence and evidence

`codingRuntimeSnapshotStore.ts` states its own scope: "durable, content-free lifecycle ledger ... intentionally has no event/token append operation: hot-path observations stay in memory" (lines 1-2). It uses Node's built-in `node:sqlite` (`DatabaseSync`, line 3), table `coding_runtime_snapshots`, capped at 10,000 rows (line 12, oldest pruned). What survives a restart: run id, state, revision, timestamps, mode/source, and six SHA-256 **digests** (task, workspace, operator, authority, binding, provenance) — never underlying text. `toolCallCount`/`patchByteCount`/`modelRequestCount` are supported columns, but the only writer, `buildStartSnapshot` (`codingRuntimeOrchestrator.ts:851-886`), always sets all three to `0` — dead columns, never written non-zero in production. Neither 2.6 transport survives a restart (in-memory only).

Evidence is separate: `codingRuntimeEvidenceAggregator.ts` emits "a single manifest ... only when a run is terminal or explicitly recovery-settled" (line 1). Its `Aggregate` type supports five observation kinds but only three — `state-transition, tool-call, model-request` — are ever emitted in production (`codingRuntimeOrchestrator.ts:752-756,1019-1024`; `productionOpenCodeBackend.ts:453-476,481-500`); `patch` and `authority-denied` are declared but unused. The evidence class on an available runtime — `"platform-qualified" | "functional-not-platform-qualified"` (`coding-workbench-runtime-api.ts:83-90`) — is a separate concept from the packaged-artifact lane label in 2.8.

### 2.8 Runtime lanes and availability

Three distinct lane concepts: (1) **`PortableRuntimeLane`** (`portableRuntimeLane.ts:17`) = `"release-qualified" | "evaluation-unqualified"` — what a _packaged artifact_ declares about its own signing (ADR-0163 D9); (2) the **dev lane** (`devLanePortableCodingRuntime.ts`, `KEIKO_CODING_RUNTIME_DEV_LANE`) — an unpackaged macOS developer-checkout lane (ADR-0140), refused outside a real dev checkout; (3) **`CodingWorkbenchRuntimeEvidenceClass`** (`coding-workbench-runtime-api.ts:77-90`) — the _UI-facing_ projection, same two label strings but a different concept.

Process supervision (`productionOpenCodeBackend.ts:373-427`) differs by lane: release-qualified gets the real native descendant-containment supervisor; the dev lane and the macOS evaluation lane share a weaker `"macos-app-sandbox"` supervisor (lines 411-427) carrying none of the release-qualified descendant-containment or orphan-reaping guarantees — macOS evaluation cannot reach the real supervisor without an Apple-entitled, notarized install; Windows evaluation is unaffected. `GET /api/coding-workbench/runtime/readiness` (`codingRuntimeRoutes.ts:208-240`) returns `runtimeAvailable` plus, only when available, `runtimeEvidenceClass` — fail-closed defaulted to `"functional-not-platform-qualified"` if unset; when unavailable, a `runtimeUnavailableReason` from a closed nine-value vocabulary (`coding-workbench-runtime-api.ts:48-58`).

### 2.9 Auxiliary capabilities

**Child agent**: built on `@oscharko-dev/keiko-harness`'s `createSession` (`productionReadOnlyChildRunner.ts:5,120`) — the only place in `coding-runtime/` that already runs a `keiko-harness` session in production. Its entire tool surface is one `ToolDefinition`, `read_file` (lines 26-34); budget: `maxCommandExecutions:0`, `maxPatchBytes:0`, `maxContextBytes:128_000`, `maxWallTimeMs:120_000`, `maxFailureAttempts:1` (lines 72-83) — distinct from the 32,768/4,096-token parent limits in 2.2/2.4.

**Skills**: the catalog seeds exactly one entry, `skl_repo-structure-summary@1`, category `repository-analysis` (`skillCatalog.ts:55-58`); the other two declared categories fail closed with `skill-handler-unavailable`. The seeded skill (`productionAuxiliaryPorts.ts:95-118`) reads `package.json`, sorts its `scripts` key names, and returns only a SHA-256 digest of that list — not the names, not a summary. It proves the pipeline, not yet a useful capability.

**Research fetch**: the narrowest trust posture in the runtime (`researchEgressPort.ts:1-27`) — GET-only, loopback denied, named-domain allowlist re-validated on every redirect hop, request-line bound to a grant digest, budget reserved before each hop, no auth/cookie headers leave, response quarantined and fenced as untrusted before the model sees it. Every outcome emits only a content-free `research-performed` event, never the URL or page.

### 2.11 Observations for the roadmap

- **`keiko-harness` has a live foothold**: the read-only child agent runs a real `createSession` today, so a Keiko-owned engine wave (S1) starts from a shipped, tested integration to widen, not an invention.
- **A complete, unmounted autonomous-delivery subsystem exists** for a future delivery wave (`autonomousDeliveryPolicy.ts`+`Routes.ts`+`ApprovalStore.ts`, 1,162 lines, compiled and tested), but `Routes.ts` is imported by zero production files (6.1 item 1); the Authority Envelope's `commandPolicy` shape, fully denied today, is the landing spot for a governed shell tool.
- **The bridge engine's App Server adapter is live, reachable code, not inert scaffolding**, wired into `codingRuntimeManager.ts` (lines 690, 2248); retiring it (Section 6) is a real removal, not cleanup.
- **Two of today's three "auxiliary" capabilities are stubs** — the seeded skill returns a digest instead of content, verification returns pass/fail with zero diagnostic detail — and the live activity feed still strips tool arguments, results, and paths, so full visibility is new work, not a redaction toggle.
- **"One active run per BFF" is one precisely-located guard clause**, not a diffuse constraint, and every governed tool call is already re-authorized live with a digest-pinned tool schema — a replacement loop must preserve both or the 2.1 trust model regresses.
- **Persisted lifecycle state is durable but empty of content** (digests and a state enum, capped at 10,000 rows), and test volume (37,782 lines) already exceeds production code (33,132) here alone — a replacement loop inherits an expectation of comparable rigor, not just comparable functionality.

## 3. Keiko-owned building blocks

Scope: the packages a Keiko-owned coding loop would be built from — `keiko-harness`, `keiko-tools`, `keiko-sandbox`, `keiko-model-gateway`, `keiko-verification`, `keiko-workflows` (context engineering), `keiko-workspace`, and `keiko-contracts`.

### 3.1 keiko-harness

**State machine.** `runLoop` (`packages/keiko-harness/src/loop.ts:177-205`) drives a 12-state machine defined in `packages/keiko-contracts/src/harness.ts:9-30`. Dispatch (`loop.ts:120-141`) routes each state to a handler in `executor.ts` (model-call, tool-call), `patcher.ts` (patch-proposal, verification, reporting), or `planner.ts` (planning, context-selection). `MAX_LOOP_STEPS = 10_000` (`loop.ts:12`) is an absolute safety net; the real bound is the budget table below.

```
intake -> planning <----------------+ retry: retryable model error (executor.ts:77)
            |                       | or failed verification (patcher.ts:51),
            v                       | while failureAttempts < max
        context-selection
            |
            v
        model-call --tool_calls (allowsTools)--> tool-call --results--> model-call
            |
            +--content, allowsPatch--> patch-proposal --> verification --> reporting --> completed
            +--content, read-only task--------------------------------> reporting --> completed

any state + abort -> cancelled | non-retryable error/contract violation -> failed
any of 7 budgets exceeded -> limit-exceeded
```

**Ports and budgets.** `ports.ts` defines `ModelPort{call, callStream?}`, re-exports `ToolPort{execute,listTools}` from contracts, plus `EventSink`, `IdSource`, `Fingerprinter`. Defaults (`packages/keiko-contracts/src/harness.ts:51-60`, `DEFAULT_LIMITS`):

| Limit                | Default                                                                 |
| -------------------- | ----------------------------------------------------------------------- |
| maxIterations        | 10                                                                      |
| maxModelCalls        | 20                                                                      |
| maxToolCalls         | 30                                                                      |
| maxCommandExecutions | 10                                                                      |
| maxContextBytes      | 512,000 (UTF-8 bytes of `JSON.stringify(messages)`, `context.ts:78-80`) |
| maxPatchBytes        | 65,536                                                                  |
| maxWallTimeMs        | 300,000                                                                 |
| maxFailureAttempts   | 3                                                                       |

**Error and recovery semantics.** Model errors (`executor.ts:57-78`, `onModelError`): abort → `cancelled`; a non-retryable `GatewayError` → `failed` (`HARNESS_MODEL_ERROR`); a retryable one increments `failureAttempts` and loops back to `planning` until `maxFailureAttempts`. Retryability is fixed per class (`keiko-security/src/errors/gateway.ts:44-159`): `TransportError`/`RateLimitError`/`TimeoutError` retry; `AuthenticationError`, `ModelRefusalError`, `MalformedToolCallError`, `ContextOverflowError`, `CancelledError`, `CircuitOpenError` do not. Tool errors (`executor.ts:463-477`): any execution failure that isn't an abort sets `HARNESS_TOOL_ERROR` and returns `{to:"failed"}` — terminal, no retry, no message fed back to the model. Tool-shaping degradation (`executor.ts:396-423`) is the one self-healing path: a throwing shaper falls back to raw output and emits `tool:shaping:degraded` without failing the run. Context/patch overflow fails closed immediately to `limit-exceeded` (`planner.ts:19-24`, `patcher.ts:17-22`, `executor.ts:369-374`) — consistent with AGENTS.md §7's "fail closed on trust boundaries." Model output is data, never an instruction (`loop.ts:1-3`): `tool_calls` are requestable only if `TaskPlan.allowsTools` is true — requesting them on a read-only task fails the run (`routeAfterModel`, `executor.ts:40-55`) — and the model cannot otherwise choose the next state, exceed its `allows*` flags, see/alter budgets, or resume/spawn sub-runs.

**Task types.** Five, not three: `generate-unit-tests`, `investigate-bug`, `explain-plan`, `verify`, `editor-agent-turn` (`keiko-contracts/src/harness.ts:70-123`; routed by `tasks/policy.ts:29-42`). `verify` never enters the loop — the BFF run engine invokes the verification orchestrator directly (`tasks/verify.ts:1-5`). Each planner emits a static, code-templated rationale string, not a model-authored plan (`planner.ts:8-15`; e.g. `` `investigate-bug: ${description.slice(0,40)}` ``, `tasks/investigate-bug.ts:39`). Production routing is narrower than the type union suggests: only `explain-plan` (`dispatchExplain`, `run-engine.ts:346-367`) and `verify` call `createSession`; `unit-tests` and `bug-investigation` route to _separate_ engines in `keiko-workflows` that never touch `keiko-harness` (3.6). The harness's own `generate-unit-tests`/`investigate-bug` builders are reachable only via the standalone `keiko-cli` (`run.ts:39-42`), wired with `DryRunToolPort` (`run.ts:390`) — even there, tool calls never touch a real file.

**Event schema, fingerprint, persistence.** `HarnessEvent` (`keiko-contracts/src/harness.ts:431-450`) is a 19-member, versioned union sharing `{runId, fingerprint, seq, ts}`: lifecycle, model-call, tool-call, sandbox/command/patch events, verification result, run-terminal, 7 `browser:*` events (a BFF surface, never routed through the loop), and `tool:shaping:degraded`. `configFingerprint` (`fingerprint.ts:10-12`) is `sha256Hex(canonicalise(...))` over `{taskType, taskInput, limits, modelId, workingDirectory, dryRun, harnessVersion}` — a config fingerprint, not a transcript hash. `MemoryEventSink` (`sinks.ts:29-46`) retains raw events for the `RunManifest` replay artifact; `CliEventSink` never prints sensitive fields. `HARNESS_VERSION = "0.1.7"`. `createSession` (`session.ts:155-196`) always builds a brand-new `RunContext` — nothing reloads prior state.

### 3.4 keiko-model-gateway

`openai-adapter.ts` is the **only** file implementing `ProviderAdapter`; no other provider's Messages-style API is implemented anywhere in the package outside tests. `ProviderEndpointStyle` (`keiko-contracts/src/gateway.ts:91`) has exactly two members — a generic chat-completions-compatible style and a cloud-deployment variant additionally requiring an explicit API version (`config.ts:610-617`). No self-hosted or local inference server gets a product-specific branch — they connect by exposing an industry-standard chat-completions-compatible surface at a configured `baseUrl`. One specific proxy product gets narrow accommodation (its own rerank adapter, `rerank-adapter.ts:1,250`; one custom auth header, `config.ts:55,62`) but is still treated as the generic style for chat, and no native adapter exists yet for any other hosted frontier-model family. The capability registry (ADR-0003), `CAPABILITY_REGISTRY := CAPABILITY_DATA` (`capabilities.ts:88`), is a **hardcoded empty array** (`capabilities.data.ts:8`) — Keiko ships no customer- or deployment-specific model ids; no built-in reference model set exists.

Native tool calling uses the standard function-call shape (`openai-adapter.ts:216-222`), parsed by `parseToolCall` (`normalize.ts:66-89`), throwing non-retryable `MalformedToolCallError` on a missing descriptor or non-JSON arguments. Streaming: `Gateway.chatStream` (`gateway.ts:248`) skips retry — a mid-stream retry would replay already-emitted tokens. The one adapter's `callStream` (570-595) streams **content tokens only** — "tool-call streaming is out of scope" (569) — tool calls arrive whole in the terminal `done` response. The live wire type `GatewayStreamChunk` is just `{delta:token:string}|{done:response}`; contracts separately declares a richer `StreamDelta.toolCallDelta` (`keiko-contracts/src/gateway.ts:639-649`) that **no adapter ever consumes** — a type slot with no wiring behind it. Embeddings/voice/rerank each get a thin adapter over the shared `gatewayFetch` seam so provider credentials never reach the browser.

Egress/SSRF: `classifyOutboundHost` (`egress-policy.ts:206-212`) buckets a host into public/loopback/private/link-local/metadata/multicast, detecting cloud-metadata IP `169.254.169.254`; `isTargetClassBlocked` (227-238) allows loopback and public by default while private/metadata/link-local need explicit opt-in and multicast is always blocked — a loopback local model server is reachable by default, a LAN-hosted one needs opt-in. `enforceOutboundTargetPolicy` (`http.ts:551-565`) re-validates every DNS-resolved address to defeat DNS rebinding, for direct calls and redirects, through the single fetch seam `gatewayFetch`.

Usage accounting: `UsageMetadata` (`keiko-contracts/src/gateway.ts:615-621`) carries `requestId, promptTokens, completionTokens, latencyMs, costClass` only — no `totalTokens`, cache, or reasoning-token breakdown; `costClass` is router-assigned, not derived from the provider's billing response. Per-call started/completed/failed log lines are keyed by a `correlationId` (`GatewayCallRequest.logContext`), per AGENTS.md §8.

### 3.5 keiko-verification and the verification loop

`buildVerificationPlan` (`plan.ts:198-215`) runs the four `SCRIPT_KINDS` — `typecheck, lint, test, build` — each mapped to `npm run <script>` when declared in `package.json`, else an explicit `skipReason`, plus optional `targeted-test` steps from changed files (`resolveTargetedTests`, 130-160) or an exact file list (`planDirectTargetedTests`, post-apply re-verification). Egress defaults to the **opposite** of `run_command`'s: `DEFAULT_VERIFICATION_LIMITS` (`keiko-contracts/src/verification.ts:45-50`) is `network:"none"` by default. `executeVerificationEnforced` (`verificationExecution.ts:58-66`) sets `networkEnforcement:"enforce-or-fail-closed"` and probes the host can wrap a run before trusting it: untrusted code is not executed otherwise. Results are a `VerificationReport`, summarized path-free/output-text-free by `summarizeForAudit`.

**Does any loop feed a verification failure back to a model?** Three sites, three answers. The harness's _own_ "verification" state (`patcher.ts:36-52`) never calls `keiko-verification` at all — only `patchDiff.trim().length > 0`; failure re-enters `planning` up to `maxFailureAttempts`, but nothing is typechecked, linted, tested, or built. `keiko-workflows`' unit-tests and bug-investigation pipelines call the _real_ orchestrator (`unit-tests/verify-stage.ts:65-99`) but only once, **after** the patch is already applied to disk (`applyAndVerify`, `unit-tests/stages.ts:205-236`), folded into a terminal `"completed"` report regardless of pass/fail; the model-loop has already exited, so there is no path back — intentional, deferred scope (`bug-investigation/verify-stage.ts:1-7`). `editor-agent-turn` is the **one exception**: `editor_request_verification` (`editor-agent-schemas.ts:289`) is dispatched by `EditorAgentToolHost.requestVerification` (`editor-agent-tool-host.ts:539-558`) to `POST /api/editor/verification/agent-runs`, backed by `executeVerificationEnforced` (`verificationRunner.ts:165`). Because this runs _inside_ the harness's tool-call state (`executor.ts:480-506`), the redacted result is appended as a `role:"tool"` message and the loop returns to `model-call` — the model genuinely sees real output and can keep iterating.

### 3.6 Context engineering (keiko-workflows)

Eight lanes (`keiko-contracts/src/context-engineering.ts:47-56`), pinned against an `effectiveInputBudget` of 116,000 of 128,000 max input tokens (`context-engineering.ts:98-106`):

| --------------------- | -------- | --------- | ----------- | ------------------- |

| user-task             | 1        | 12,000    | 8,000       | none                |
| active-plan           | 2        | 16,000    | 0           | summarize-then-drop |
| working-memory        | 3        | 24,000    | 0           | summarize-then-drop |
| repo-evidence         | 4        | 48,000    | 0           | drop-lowest-score   |

| history-summary       | 6        | 16,000    | 0           | summarize-then-drop |

(`context-budget/defaults.ts:19-72`.) `allocateContext` (`allocator.ts:273`) is pure/deterministic: non-evictable lanes always fully included even over cap; evictable lanes fill in priority order. `buildCompactionRecords` (`compaction.ts:155-168`) emits one `ContextCompactionRecord` per evicted lane (reason, before/after counts, `summaryRefHash`, provenance `sourceSpans`) plus a `ContextRehydrationHandle` so an evicted item can be re-fetched and checked for staleness. Observation shapers (`observations/`): `command.ts` (redacted byte-bounded excerpts), `search.ts` (top-scoring ranges only, no raw atom text), `test.ts` (no per-test pass/fail names, since the live `VerificationResult` carries none), `shared.ts` (redact()-first, content-free injection detection). This subsystem is CI-gated by a measured, not declared, fidelity check (`npm run check:context-quality`) over a fixed, seeded corpus: nine hard invariants (fact/instruction/diff/failing-test preservation, line-ref accuracy, injection isolation, redaction, path-free compliance, determinism) plus three softer floors — `minRehydrationReadiness ≥ 0.9`, `minCompactionPreservation ≥ 0.8`, `minToolObservationShapingFidelity ≥ 0.9`.

**The harness does not consume any of this.** `keiko-harness` has zero import edges to `keiko-workflows` (`context.ts:34-35`); the 8-lane allocator is wired only into the chat prompt path (`chat-prompt-budget.ts:258`). The harness's own `contextBytes` (`context.ts:78-80`) is a flat UTF-8 byte sum against one ceiling — no lanes, priority, eviction, or rehydration. The only bridge, `HarnessShaperPort`, is wired in production to exactly one of the three shapers — `shapeCommandObservation`, scoped to `run_command` only (`keiko-server/src/harness-tool-shaper.ts:12,68`); the search and test shapers are never wired to the harness.

### 3.7 keiko-workspace boundary

Two layers, both reused by every tool above. **Lexical containment** — `resolveWithinWorkspace` (`paths.ts:16-32`), pure, no filesystem access: rejects a NUL byte or a `..`-escape, throws `PathEscapeError`. **Symlink containment** — `containedRealPathInfo`/`assertContainedRealPath` (`realpath.ts:56-99`), realpath-following via the injected `WorkspaceFs` port, defending the ".git/hooks escalation" class by realpath-ing the nearest _existing_ ancestor for a not-yet-created target — the read path (`discovery.ts`) and write/cwd paths (`tools/patch.ts`, `tools/exec.ts`) share this single primitive.

Sensitive-path denial is a separate, always-on gate: `DEFAULT_DENY_PATTERNS` (`ignore.ts:12-45+`) — `.env`/`.env.*`, `*.pem`/`*.key`, `id_rsa`/`id_ed25519`/`id_ecdsa`/`id_dsa`, `*.p12`/`*.pfx`, `.npmrc`, `.ssh`, `.aws`, `.gnupg`, `.kube`, `.azure`, `.docker`, `.netrc`, `.pgpass`, `.git-credentials`, keychains, `.keystore`/`.jks`, `.config` — enforced by `isDenied()` "before every read regardless of .gitignore," never relaxed by the separate best-effort `.gitignore` matcher.

The full chain a new tool must run is `resolveReadableWorkspaceFile` (`discovery.ts:295-335`): boundary → deny (lexical) → realpath containment → symlinked-root deny check → deny again on the realpath-resolved path → hard-link-alias rejection → size cap; `readWorkspaceFile` (338+) adds a final `redact()` pass. `WorkspaceToolHost.readFile` (`registry.ts:175-180`) routes through this already. A new model-callable shell/file tool has no sanctioned alternative — it must call through `discovery.ts`'s exported functions, never `node:fs` directly.

## 4. User interface

### 4.1 Entry points and shell integration

`"coding"` is one member of the desktop shell's `WindowType` union (`packages/keiko-ui/src/app/components/desktop/windows/WindowsRegistry.ts:26`), registered as `tool: true, singleton: true`, default size 860x600, icon `"code"` (`WindowsRegistry.ts:475-490`). `singleton: true` means exactly one instance can be open — the shell's generic `toggleTool` mutation un-minimizes and focuses an existing "coding" window, closes it on a second toggle, or opens one if absent. Two reachability paths call the same `toggleTool("coding")`: a dedicated Left Rail button and the quick-access palette (`quickAccessRegistry.ts:44-48`); no task-creation flow exists distinct from opening this singleton window.

Multi-workspace behaviour is shell-inherited: `ActiveWorkspaceContext` is the single shared binding source of truth — one active `WorkspaceBinding` at a time, a switch retargets all surfaces atomically (`ActiveWorkspaceContext.tsx:5-45`). The Workbench has no independent per-window workspace picker — always bound to whichever repository is active shell-wide, consistent with the "exactly one active run per BFF" constraint (ADR-0137) a later wave lifts.

### 4.2 Screens and states

`WorkbenchColumns` branches on one boolean, `showSetup = bootstrapSetupVisible(state, activeWorkspace)` (`CodingWorkbenchWindow.tsx:251`; true whenever no binding and no workspace value are set).

**Setup screen** (`CodingWorkbenchSetup.tsx`) has two text fields — repository path and target branch, defaulting to `"main"` — and one submit button whose label cycles `Bind` → `Binding…` → `Verifying…`. Submission calls `bindVerifiedTaskWorkspace`: provision → reconcile → activate (`verified-task-workspace-binding.ts:125-163`) — provision creates the worktree; reconcile stamps the verified Git head the launch authority requires and must report `"healthy"` or the bind fails at `"verify"`; only then does activate set it active. Failures degrade to one of three bounded, content-free notices — `bind`, `verify`, `branch-conflict` — never raw server text. A runtime-assurance note keeps a fresh evaluation install from implying a platform-qualified runtime it does not have (ADR-0163 D9).

**Session screen** is a single vertical stack, not a two-column layout: `.session` is `display: grid; grid-template-rows: minmax(0, 1fr) auto` (`CodingWorkbenchWindow.module.css:146-154`) — a scrollable `role="log"` stream on top, a docked composer pinned to the bottom. No task-list/session-list pane exists; a two-column "task list left, session right" layout is not yet built (4.9).

Header labels come from `WorkbenchHeader`/`headerStateLabel` (`CodingWorkbenchSections.tsx:21-69`): the idle pill checks the aggregated `canStart` before it will ever say "ready" — `blockedIdle = snapshotState === "idle" && !state.canStart` — rendering "Not ready to start" instead of a plain idle label. An unverified evaluation runtime overrides the idle label to "Start — unverified evaluation runtime." Other run states: `Ready to start`, `Starting`, `Runtime ready`, `Running`, `Paused`, `Approval required`, `Stopping`, `Succeeded`, `Failed`, `Stopped`, `Taken over`, `Recovery required`.

`canStart` is computed by `projectReadiness` (`packages/keiko-ui/src/lib/coding-workbench-live-state.ts:231-272`):

| #   | Condition        | Requires                                                                                                                   | Source             |
| --- | ---------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 1   | `sourceReady`    | selected model source `ready`, matches current `runtimePreference`, `available`, verification doesn't contradict readiness | `:238-242`         |
| 2   | `workspaceReady` | workspace resource `ready`, health `"healthy"`, not mid-switch                                                             | `:243-246`         |
| 3   | `authorityReady` | runtime readiness `ready`, `runtimeAvailable === true`, server-confirmed mode matches requested mode                       | `:247-250`         |
| 4   | `runReady`       | run resource `ready`, state in `idle/succeeded/failed/cancelled/taken-over`                                                | `:211-217,251-253` |
| 5   | `mutationIdle`   | no mutation currently `pending`                                                                                            | `:254`             |
| 6   | `pairingReady`   | window server-confirmed `paired` (fails closed on `"unknown"`, ADR-0141)                                                   | `:255-258`         |

`canStart` = all six, ANDed (`:261-262`); `canRetry` is the same set minus `runReady`, replaced by `recovery-required` + `recoveryAcknowledged` (`:263-270`).

### 4.3 Composer

`TaskStartSection` (`CodingWorkbenchSections.tsx:78-169`) is the only input surface: one `<textarea>`, `maxLength={65_536}`, Enter submits, Shift+Enter newlines — no mode selector, model picker, or attachment control. The send button's action depends on `runState`: `onStart` idle/terminal, `onPause` while `"running"`, `onSend` (follow-up) while `"paused"`.

Two inputs shape the request without being chosen in the composer. Autonomy mode syncs from the shell-wide `useAutonomyModePolicy()` hook by an effect, not picked per task. Runtime preference (`managed-gateway` vs. the retired subscription-lane source) defaults to `"managed-gateway"`; its only control, `CodingWorkbenchModelCards.tsx`, has **zero production mount points** — imported only by its own test file, `setRuntimePreference` has no other caller — so runtime preference is always `managed-gateway` in the shipped app; the retired-lane path is implemented but unreachable by any user action (the dead selector Section 6 covers).

### 4.5 Client state and transports

All Workbench state is in-memory React state behind one reducer (`coding-workbench-live-state.ts`), composed by `useCodingWorkbenchRuntime` (`useCodingWorkbenchRuntime.ts:59-100`) from resource hooks, a serialized mutation queue, and stream/pairing/workspace effects. No `localStorage`/`sessionStorage` use exists in this tree.

**Transport 1 — content-free `EventSource`.** `createCodingWorkbenchRuntimeEventSource` opens `GET /api/coding-workbench/runtime/runs/{runId}/events[?cursor=…]`. `RuntimeEventStreamSession` (`coding-workbench-event-retention.ts:85-228`) batches events every `100`ms, reconnects on a `35_000`ms silence watchdog, and on a server `"reset"` event closes, clears events, refreshes the run, and bumps a `streamEpoch`. The client buffer caps at 500 events, evicting ordinary events before "pinned" ones (approval/recovery/terminal/permission-requested).

**Transport 2 — content-bearing authenticated fetch-stream.** `streamCodingAppSessionChannelSnapshots` avoids `EventSource`: content-bearing activity stays on the cookie-authenticated app-session channel and never widens the content-free runtime SSE union (`coding-app-session-channel-api.ts:57-60`). It reads `GET /api/coding-workbench/app-session/channel/stream` via `fetch` + `ReadableStream` to attach a correlation-id header and parses `event: snapshot`/`data:` frames itself, treating `45_000`ms without a byte as a stall against a documented 15s server heartbeat.

**On page reload**, an effect unconditionally calls `refreshRun()` → `GET /api/coding-workbench/runtime/status`; once the returned snapshot's state is streamable, the `EventSource` stream reattaches automatically — driven entirely by server truth, not a client-persisted run id. The active task-workspace binding is independently re-verified on restore (`verified-task-workspace-binding.ts:99-114`); window pairing re-resolves fail-closed to `"unknown"` on any read failure.

### 4.6 Editor bridge

`useCodingWorkbenchEditorBridge` registers a headless session on the same shared bridge primitive the real Editor window uses (ADR-0060/ADR-0061). `INERT_BRIDGE_CONTROLLERS` (`:191-207`) stubs every controller except `applyChangeset`: verification checks always pass, `persist` always resolves `false`, `currentText` always returns `""`, edit calls are no-ops — every other action type is either not applicable headless or already fails closed. `handleApplyChangeset` (`:242-255`) auto-succeeds when `action.requiresReview === false`, otherwise stages a parsed unified diff as `pendingReview` for `ChangesetReviewPanel`. The headless snapshot carries no panes, no active file, and `diagnosticsSummary: null`. Decision delivery retries at `[150, 400, 900]`ms, then forces a bridge reconnect and retries once more; an undelivered decision surfaces as `deliveryFailed`, never silently cleared.

## 5. Governance and authority

Every Coding Workbench capability — today's and any roadmap extension — runs inside one authority system: a single mode contract (`CodingWorkbenchMode`), one monotonic effect matrix, one Authority Envelope minted per run, and one per-tool-call authority port.

### 5.2 Mode semantics as implemented

The three modes are one closed union (`CodingWorkbenchMode`, `coding-workbench.ts:6`), each with a `CODING_WORKBENCH_MODE_POLICIES` entry (`:330-444`) holding an `effects` matrix over 4 resource scopes × 4 approval risks — 3×16 = the 48-cell table ADR-0138 D2 names explicitly (`docs/adr/ADR-0138-monotonic-product-wide-autonomy-semantics-and-code-task-terminology.md:68,110`), pinned by `coding-workbench.test.ts:292-307` (`strictestCodingWorkbenchPolicyEffect(lower, higher) === lower` for every adjacent mode pair, scope, and risk — raising the mode can never make any cell stricter).

| Resource scope                     | Ask for approval  | Supervised workspace | Full access       |
| ---------------------------------- | ----------------- | -------------------- | ----------------- |
| workspace-contained, low/medium    | approval-required | **allowed**          | allowed           |
| workspace-contained, high/critical | approval-required | approval-required    | **allowed**       |
| external-file (all risk)           | approval-required | approval-required    | **allowed**       |
| internet (all risk)                | approval-required | approval-required    | **allowed**       |
| delivery (all risk)                | approval-required | approval-required    | approval-required |

The task's six action classes map onto this matrix and one further, mode-invariant gate:

- **read / discover** — `codingToolAuthorityPort.ts:328-330` returns `true` unconditionally, no resource-scope check; reads are ungated by mode by design.
- **workspace edit** — also returns `true` at the authority-port switch (`edit` case, same lines); containment is enforced separately and mode-_invariantly_ by `decideSupervisedFileEdit()` (`supervisedCodingPolicy.ts:95-101`, realpath containment against `allowedRelativePaths`) for the `codex-cli-adapter` sidecar path, and by the tool-IPC parse boundary (`codingToolIpc`) plus the `keiko-tools` contained writer for the native path (comment at `codingRuntimeManager.ts:2688-2694`); whether the edit needs _approval_ is the workspace-contained/risk cell above, in a separate per-runtime-source dispatcher below.
- **command** — gated by `workspaceMediumRiskAllowed()` AND `commandAllowed()` (`codingToolAuthorityPort.ts:333-336, 387-397`), reading `envelope.authority.commandPolicy`.
- **external file / internet (research)** — the `external-file` and `internet` rows.
- **delivery** — flat `approval-required` in all three modes; see 5.5.

**Two enforcement call sites read the same table**, one per runtime source: for the `codex-cli-adapter` (bridge engine) sidecar, `codingRuntimeManager.ts:2667` (`autonomousDeliveryRuntimeEvent`) and `:2696-2704` (`supervisedCodingRuntimeEvent`) both branch on `active.effectiveMode` and delegate to one shared dispatcher, `governedActionRuntimeEvent()` (`:2707-2717`) — so Full access is structurally incapable of being stricter than Supervised workspace for the same action. The `keiko-sidecar` native path instead runs every IPC action through `codingToolAuthorityPort.ts` directly — one policy source of truth, two call sites that must stay synchronized while both runtime sources coexist.

**Fail-closed by absence, verified.** `command` is plumbed end-to-end — contract type (`codingToolIpc.ts:62-65`), authority-port gate, governed delegate — but `productionRuntimeWorkspaceAuthority.ts:113-119` mints every envelope with `commandPolicy: { mode: "deny", allow: [], deny: [], maxCommandTimeoutMs: 1, requirePerCommandApproval: true }`, hardcoded, independent of mode. `commandAllowed()` (`:387-397`) denies outright whenever `policy.mode === "deny"`, so despite the matrix marking workspace-contained/medium `allowed` in supervised-coding and autonomous-delivery, **no mode has a working generic command-execution path today** — those cells are allowed-on-paper, denied-by-construction. `verification` is a narrower, working exception: `:332-333` gates it only through `workspaceMediumRiskAllowed()`, bypassing `commandPolicy` entirely, and `DEFAULT_SUPERVISED_VERIFICATION_COMMANDS` (`supervisedCodingPolicy.ts:83-93`) already allowlists `npm run typecheck/lint/format:check/test`, `arch:check[:negative]`, and `git status --short`.

### 5.3 Approval, question and grant mechanics

**Approvals** (workspace-write / command-execution / delivery-substrate risk cells). A denied or approval-required tool decision produces a `CodingWorkbenchPermissionRequest` (`coding-workbench.ts:571-579`) that a run in `awaiting-approval` state surfaces via `pendingPermission()` (`codingRuntimeOrchestratorState.ts:62-64`) into the public snapshot. The human answers `POST /api/coding-workbench/runtime/runs/:runId/approvals` (`codingRuntimeRoutes.ts:598-601`), handled by `decideApproval()` (`codingRuntimeOrchestrator.ts:438-467`): the presented challenge is marked `used = true` before any side effect, an approved decision mints authority via `issueApprovedAuthority`, `permissionPort.resolve()` is notified, and the approval record is deleted from the in-memory store regardless of outcome — a challenge cannot be replayed either way.

**One-use refs** (ADR-0125). `authorityRef` is `{ runId, envelopeDigest }`: the server accepts an externally-referenced envelope only against a server-minted, one-use confirmation, storing the validated envelope behind the opaque reference (`docs/adr/ADR-0125-governed-agent-docking-and-editor-changesets.md:126-128`). `approvalRef` is `{ approvalId, boundActionId, proofDigest, expiry }`; an unissued reference fails closed, and the contract never carries a reusable bearer secret (same file, :128-129). `consumeConfirmation()` (`runtimeAuthorityService.ts:565-583`) cross-checks `taskId`/`operatorId`/`intentDigest` then calls `this.approvals.consume(...)`, which removes the confirmation on use.

**Questions** are distinct from approvals: `productionCodingRuntimeQuestionPort.ts` wraps the bridge engine's `listQuestions`/`answerQuestion`/`rejectQuestion` (interactive clarification the bridge raises mid-run), routed through `/runs/:runId/questions[/answer|/reject]` — content-bearing routes swept by `contentRouteEnforcement.test.ts:23-28` (5.6). They do not mint or consume authority; they carry model-directed questions and human-directed answers.

**Research grants** are the narrowest authority object: `researchEgressPort.ts` is the only way a Code task reaches the public internet (`:1-3`), GET-only, no cookies/authorization headers ever sent, host-allowlisted on the initial request and every redirect hop, request-line-digest bound. `researchGrantRegistry.ts:171-196` clamps every grant's expiry to `min(requested expiresAt, now + maxGrantTtlMs)` server-side. `POST /runs/:runId/research/revoke` (`codingRuntimeRoutes.ts:367,638-641`) lets the human end a live grant early; fetched page content is quarantined as `untrusted` before the model sees it (`researchContentQuarantine.ts`; contract type `CodingWorkbenchContentTrust = "untrusted"`, `coding-workbench.ts` ~line 409).

### 5.5 Git delivery governance today

`executeGovernedMutation()` (`gitDelivery/execution.ts:171-194`) runs one governed local mutation end-to-end through the kernel `runGitMutation` (`execution.ts:20,185`): live worktree snapshot → policy evaluation → approval-requirement resolution → execution → evidence, appended before the caller's response. Four **separate, non-overlapping execution authorities** exist as `keiko-tools` gateways, deliberately not layered on one another (each file's header says so): `git-commit-intent-node.ts` (local commit), `git-publish-gateway.ts` (push), `git-pr-gateway.ts` (PR create/update via `gh api`; allowlist "create / update / get / the draft GraphQL mutations — NO merge, NO delete," `:7`, with full draft↔ready support, `:71,94,248,284-289`), and `git-merge-gateway.ts` (a third parallel execution authority with its own dedicated `gh api` allowlist, `:4-9`, ADR-0087). A protected-branch constraint is evaluated once, centrally, in `git-delivery-policy.ts:253-262` — deliberately evaluated here and not inlined at the four gateways, since four copies of a denial is four places for it to drift apart — failing closed on an unresolvable target branch.

At the coding-workbench layer, `delivery` is `approval-required` in **all three** modes uniformly (5.2 table) — no per-mode split between commit, push, pull-request, and merge; `agentOperationsRoutes.ts:456-457` calls this intentional: fetch/pull/push/pull-request/merge are approval-required at every mode, per ADR-0087. A finer split (commit/push/draft-PR pre-approved once per run vs. merge always approved) is expressible one layer down, in `GitDeliveryApprovalRequirement` (`git-delivery.ts:235`), which already supports `{ required: false }` as a legal value.

Scaffolding for exactly this already exists, unmounted: `AUTONOMOUS_DELIVERY_ROUTE_GROUP` (`coding-runtime/autonomousDeliveryRoutes.ts:632-642`, routes `.../autonomous-delivery/confirm` and `.../execute`) is defined but never imported into `routes.ts` (every other route group there is spread with `...X_ROUTE_GROUP`; grepping the server tree for the constant outside its own file and tests returns nothing). Mounted, it would let one `AutonomousDeliveryConfirmation` (`.../confirm`, one approval proof digest) authorize a batch of steps (`.../execute`) — `repository-operation` (via `handleGitAgentOperation`), `command-task`, or `connector-operation` — each re-checked by `decideAutonomousDeliveryOperation()` (`autonomousDeliveryPolicy.ts:160-168`) for branch/scope containment before executing. `autonomousDeliveryPolicy.ts:255` already reads `commandPolicy.mode !== "deny"` for command-task steps, inheriting 5.2's fail-closed-by-absence gap directly. This scaffolding is therefore mostly a mounting and policy-population exercise over already-reviewed gateways, not new execution machinery; the merge gateway and the protected-branch constraint are untouched by it.

### 5.6 Evidence and redaction rules

`CodingWorkbenchEvidenceRecord` (`coding-workbench-evidence.ts:31-49`) is body-free by field design: every field is an enum, id, digest, count, or a `safeSummary` string constrained by `SAFE_LABEL_PATTERN`/`REDACTED_SUMMARY_PATTERN` (`:52-58`) — never raw text. The same file defines secret/URL/command-log/diff detection patterns (`SECRET_PATTERN`, `BEARER_CREDENTIAL_DETECTION_PATTERN`, `COMMAND_LOG_PATTERN`, `DIFF_PATTERN`, `:59-68`) that reject a `safeSummary` leaking content rather than merely omitting it. The runtime SSE observation channel (`CodingWorkbenchRuntimeEvent`, `coding-workbench-runtime.ts` ~line 218-250) mirrors this: `diff-summarized` carries `fileCount`/`addedLines`/`deletedLines`, never a diff hunk; `verification-summarized` carries pass/fail/skip counts, never log text; `research-performed` carries a byte count and the constant `contentTrust: "untrusted"` marker, never a URL or page byte.

### 5.8 Landing spots for capability growth

The pattern that recurs across 5.2–5.6 is the same in every case: extend an existing table or port rather than add a parallel mechanism.

- **A governed shell** extends `commandAllowed()` (`codingToolAuthorityPort.ts:387-397`), already the per-command gate; the change belongs in the envelope constructor, `productionRuntimeWorkspaceAuthority.ts:113-119`, which must stop hardcoding `mode: "deny"` and instead derive a `CodingWorkbenchCommandPolicy` per `effectiveMode`. `command` stays a `command-execution` action, so it still passes the 5.2 workspace-contained risk cell first — a widened `commandPolicy` must never bypass that cell.
- **Full live visibility** extends the existing content-bearing pattern (5.6): new SSE fields or routes carrying command text/arguments/output/diff bodies join `resolveAppSessionReadAuthority()` exactly as `questions`/`research` do today, and join `ENFORCED_CONTENT_ROUTE_PATTERNS` in `contentRouteEnforcement.test.ts:23-28` so the unauthenticated sweep keeps covering them. `CodingWorkbenchEvidenceRecord` and the `CodingWorkbenchRuntimeEvent` status channel stay body-free — new content lives only in the paired live stream.
- **Unattended branch delivery** mounts `AUTONOMOUS_DELIVERY_ROUTE_GROUP` (`autonomousDeliveryRoutes.ts:632-642`) into `routes.ts` and populates `GitDeliveryApprovalRequirement` (`git-delivery.ts:235`) so commit/push/draft-PR resolve `{ required: false }` once a single confirmation is held, while merge stays `{ required: true }` unconditionally — `git-merge-gateway.ts` and the centralized protected-branch constraint (`git-delivery-policy.ts:253-262`) are untouched. The `delivery` resource-scope row stays `approval-required` in all three modes at the coding-workbench layer (5.2/5.5) — Full access satisfies that gate once, at envelope-confirm time, never per merge.
- **An MCP client** extends `CodingWorkbenchConnectorScope` (`coding-workbench.ts:57-63`), a closed 6-value union (source-control/issue-tracker/knowledge-base × read/write), and `connectorAllowed()` (`codingToolAuthorityPort.ts:376-385`), which already double-gates on `envelope.authority.connectorScopes` AND `envelope.authority.networkPolicy.connectorScopes`. Server trust registration extends this scope union (e.g. a namespaced `mcp.<server-id>.*` family) rather than building a parallel tool-authority path; each MCP tool call becomes a `connector` IPC action carrying the registered scope. The double-gate stays, so a connector scope alone can never open network egress.
- **Parallel/resumable runs and writing sub-agents.** `CodingRuntimeAuthorityService` holds one `runtimeState` field process-wide; `mintConfirmedStartForRun()`/`mint()` both check `this.runtimeState.state !== "idle"` (`runtimeAuthorityService.ts:184,207`), matching ADR-0137 D2's "V1 permits exactly one active run per BFF." Lifting this means keying runtime state and `activeAuthorityRef` by workspace/worktree instead of one instance-wide field — each parallel run needs its own worktree-scoped binding through `resolveProductionRuntimeContext()` (`productionRuntimeWorkspaceAuthority.ts:63-73`), which already reads one specific `workspaceLifecycle.getActive()` binding per call and could accept a worktree identifier instead. Budget inheritance for writing sub-agents should extend `EditorAgentAuthorityRegistry` (`agentAuthorityRegistry.ts`) with a parent-child budget relationship rather than a new accounting store; `child-agent` is already a recognized `CodingToolAction` (`codingToolIpc.ts`) with its own `maxToolCalls` field, so the contract slot exists. `task-workspace`'s active-binding singleton (`task-workspace/active-store.ts`) is the one workspace registry — parallel runs must be modeled as multiple provisioned-and-bound worktrees inside it, never a second registry.

## 7. Capability parity against the market baseline

### 7.1 How leading agentic coding assistants work a task

Leading agentic coding assistants share one execution model across their surfaces (CLI, IDE extension, desktop app): the operator states a task and, optionally, the assistant plans in a read-only mode requiring approval before any edit begins. Once acting, the assistant runs a model-driven tool loop — file read/search tools, a shell/command tool (sandboxed by an OS-level isolation backend locally, or an isolated remote container), and an edit/patch tool that shows a diff before or after apply — with every tool call and its streamed arguments and results visible live to the operator. Two axes gate risk: a permission profile or mode (from fully manual per-action approval through automatic edit-acceptance to a bypass mode) and, in some products, a separate approval policy for command execution; an optional automated pre-action reviewer can add a further check. The assistant re-runs verification (tests, typecheck, lint, build) itself and iterates on failures without a separate "self-repair" toggle, then — once the operator reviews the diff — commits, pushes, and opens a pull request, explicitly rather than silently. Sessions persist to a local transcript, can be resumed or forked, and can spawn sub-agents with their own context and tools, optionally in an isolated worktree; a per-repository instructions file, loaded through an override chain, injects project memory into every turn. The loop is scriptable headlessly and embeddable through a published SDK, extensible through tool-protocol servers, skills/slash commands, and lifecycle hooks, and every tool or command can be scoped by allow/deny/ask rules. Remote/cloud execution, desktop-specific worktree automation, and the published SDKs are surface-specific; the plan → tool-loop → verify → deliver core is identical across surfaces.

### 7.3 Tier proposal rationale

**Must** items are either (a) load-bearing for the "plan → tools → iterate → verify → deliver" core the parity target defines, or (b) already owner-accepted assumptions (token/cost display, per-run model selection, plan artifact, full tool cards), or (c) existing Keiko strengths (rows 29–30) that a roadmap must protect while closing other gaps, not trade away. Row 2 (Plan mode) is Must because dogfooding an issue end-to-end means the operator has to see and approve a plan before the agent commits to an approach — today's `todowrite` is a running log, not a gate. Row 4 (governed shell) is Must because Decision 2 already names it as the next capability to build, and rows 5–6 (fine-grained permission rules, content search) are Must because they are the load-bearing prerequisites a governed shell needs on day one — a shell tool without allow/deny/ask rules or a way to search before running a command is not "modelled on" the market baseline per Decision 2, it is a bare exec. Rows 7–8 (diff-reviewed edit, verify-and-repair) are Must because they already work and are, on the evidence above, stricter than the market baseline (hash-bound patches, a mandatory verification tool rather than emergent behavior) — the roadmap's job here is not to build but to not regress.

**Should** items extend the core loop to match what "a task" means once it runs longer than one sitting or touches more than the local machine: session persistence (13) unlocks background tasks (12), context compaction (14), and true multi-project work (26); worktrees (10) and deeper sub-agents (11) unlock parallel Code tasks; MCP client (18), broader research/web access (21), project-memory loading (23), and a wider editor bridge (24) round out what an operator already expects from the market baseline but that does not block a first dogfooded issue. Git delivery (9) is Should, not Must, because unattended commit/push/draft-PR is explicitly scoped to Full access mode and later waves — the human-triggered path already works today.

**Later** items are real gaps but do not block the dogfooding acceptance test and are not on the core-loop yardstick: skills/hooks/notifications/image input are polish and extensibility, not the mechanics of working a task; cloud execution is explicitly out of scope by product design (Decision 8); headless/SDK usage already has a narrow, real starting point (`keiko run`) that later waves can widen once a Keiko-owned engine matures.

### 7.4 Where Keiko already exceeds the market baseline

Neither reference product documents a redaction or compliance layer over its own session data — both keep full, content-bearing local transcripts or session logs by design. Keiko's `CodingWorkbenchEvidenceRecord` instead ships as a closed, validated shape whose text fields are canonicalized through explicit redaction tokens — `redacted-url`, `redacted-path`, `redacted-command-log`, `redacted-content`, `redacted-auth`, `redacted-credential` (`packages/keiko-contracts/src/coding-workbench-evidence.ts:57-72,599-602`) — so persisted evidence and diagnostics are body-free by construction, per Decision 4 and AGENTS.md §1, while the local human still sees full commands, output, and diffs live in the stream.

Keiko's file-edit tool binds every patch to a SHA-256 `expectedContentHash` captured by the most recent read, and instructs the model to re-read and rebuild the patch on a mismatch rather than retry blind (`opencodeToolSchemas.ts:93-118`; `opencodeLaunchProfile.ts` step 4) — a TOCTOU-safe edit discipline neither reference's plain diff-and-apply flow documents. The research-fetch path narrows an entire fetched page through a hardened HTML scanner, fences the surviving text in a sha256-keyed untrusted-data envelope, and neutralizes every literal marker token before the model ever sees it (`researchContentQuarantine.ts:1-19`) — explicit prompt-injection engineering that goes beyond a permission-gated fetch tool. Sub-agents are budgeted at the token and tool-call level and structurally capped at one layer (`productionReadOnlyChildRunner.ts`), and every autonomy mode resolves to the fail-closed minimum of the requested mode and the deployment ceiling — never the reverse (ADR-0124 D2; ADR-0129) — an invariant stricter than the market baseline's mode/profile systems. Finally, the authenticated local app-session channel (ADR-0141) binds content-bearing Workbench state to a launcher-paired session rather than an ambient local process, a trust boundary purpose-built for the regulated, local-first posture AGENTS.md §1 states as non-negotiable.

## 9. MemoriaViva and persistence reuse

Decision 12 (owner statement): MemoriaViva is the only memory system — "we do not want a parallel world." Every memory-, knowledge-, transcript- or session-persistence need of the coding engine extends MemoriaViva and the existing server store patterns; this section verifies what that means concretely.

### 9.1 What MemoriaViva is

MemoriaViva is five independent leaf packages orchestrated by `keiko-server`, not one library: `keiko-memory-capture` → `keiko-memory-consolidation` → `keiko-memory-governance` → `keiko-memory-retrieval`, plus `keiko-memory-vault` for storage. Per `.dependency-cruiser.cjs` rules `adr-0019-direction-3f`..`3j` (`.dependency-cruiser.cjs:386-561`), all five may depend only on `keiko-contracts` + `keiko-security` — not on each other, and not on the vault (capture, consolidation, governance, and retrieval are all vault-blind; only `keiko-server` wires vault reads into them). Rule `6a` (`.dependency-cruiser.cjs:663-690`) makes `keiko-server` the **only** package in the graph allowed to combine any `keiko-memory-*` package with `keiko-model-gateway`. This is the load-bearing fact for the roadmap (S6): any coding-engine/memory integration that needs both a model and memory must be composed in `keiko-server`, not inside `keiko-harness`.

**Record model** (`packages/keiko-contracts/src/memory-records.ts:96-131`, `packages/keiko-contracts/src/memory.ts`): a `MemoryRecord` has `id`, `schemaVersion: "1"`, a discriminated `scope` (`user | workspace | project | workflow | global`, `memory.ts:72-84`), a `type` (8 values — `episodic, semantic-fact, procedural, preference, correction, decision, negative, pinned`, `memory.ts:86-104`, each with a type-aware decay half-life multiplier per ADR-0117, `memory.ts:121-129`), `body`, an optional structured `payload`, mandatory `provenance` (`sourceKind`, `capturedAt`, `confidence`, `sensitivity`, `memory-records.ts:58-76`), a `validity` interval, an 8-state `status` lifecycle with a pinned transition matrix (`memory.ts:170-202`), `pinned`, `staleReason`, `retentionHint`, and `tags`.

**Mode-aware capture** (ADR-0146, `docs/adr/ADR-0146-mode-aware-memory-capture.md`): capture reuses `CodingWorkbenchMode` from `keiko-contracts` — no memory-local autonomy model (D1). Hard, mode-independent denials run first (D3): secret-bearing bodies are dropped; `restricted` sensitivity is rejected; `confidential` is capped at `proposed` in every mode. For candidates that clear those gates, mode picks the target status (D2): `governed-assist` → `proposed` (held for review, excluded from retrieval); `supervised-coding`/`autonomous-delivery` → eligible for `accepted`. Eligibility is not a bypass of governance (D4): every capture entry point — salience (`captureSalientFromTurn`, `packages/keiko-server/src/memory-salience.ts:745`), explicit chat intent, voice recap, capture-from-conversation — routes through one function, `promoteEligibleMemoryRecord` (`packages/keiko-server/src/memory-capture-policy.ts:213`), which calls the same `planMemoryMaintenance`/`shouldPromote` lever the standing maintenance sweep uses. Sensitivity classification itself (`classifySensitivity`/`applyPolicy`, `packages/keiko-memory-capture/src/policy.ts:1-71`) is content-based and mode-independent.

**Conflict review**: `detectConflictPair` (`packages/keiko-memory-governance/src/conflict.ts:1-29`) is a pure pairwise predicate (`negation-flip`, `polarity-mismatch`, `value-mismatch`) feeding governed `ReviewItem`s. ADR-0120 adds one **optional, server-only** enrichment: a model-generated resolution suggestion, gated behind `KEIKO_MEMORY_CONFLICT_ADVISORY` (default off) and implemented entirely in `keiko-server` (`memory-conflict-advisory.ts:61`) _after_ the pure consolidation engine returns — `runConsolidation`/`detectConflicts` themselves stay synchronous, IO-free, and byte-identical (`packages/keiko-memory-consolidation/src/consolidate.ts:1-13`). This is the one place MemoriaViva content crosses the model-gateway trust boundary today, and it required its own ADR-0120 triage per AGENTS.md §12 — precedent any future memory↔model crossing must repeat.

**Encryption at rest** (ADR-0035): AES-256-GCM via a `keiko-security` secretbox primitive. Content columns are sealed, index/metadata columns stay cleartext — verified directly in `packages/keiko-memory-vault/src/serialize.ts:54-58` (open) and `:70-74` (seal): `body`, `payload_json`, `tags_json`, `capture_rationale`, `stale_reason` are sealed; ids, `scope_kind`, `status`, timestamps etc. are not. Key precedence (`packages/keiko-memory-vault/src/cipher.ts:1-38`): `KEIKO_MEMORY_KEY` env → macOS Keychain → `<memoryDir>/vault.key` (mode 0600).

**ANN retrieval runtime** (ADR-0164): one shared service, `searchUsearchAnnIndex` in `keiko-local-knowledge`, composed by everything under a closed `knowledge | repo | memory` namespace union on `VectorIndexPort`. Memory's composition is `packages/keiko-server/src/memory-retrieval-signals.ts:352-360,421-422` (`createMemoryVectorIndexPort`, `namespace: "memory"`), which passes a bounded `candidateIds` allow-list so only already-authorized, already-decrypted memory vectors ever enter the index — no second plaintext copy. `retrieveMemoryContext` (`packages/keiko-memory-retrieval/src/retrieve.ts:389-426`) is the single entry point: scoped fetch → dedupe → filter → rank (lexical + semantic + strength + graph) → MMR diversity → token-budgeted assembly, returning both `included` and `omitted` with typed reasons.

### 9.3 How memories reach a model today

Desktop chat: `retrieveChatMemory` (`packages/keiko-server/src/chat-handlers.ts:1212-1239`) calls `retrieveMemoryContext` with scopes + query text + semantic/strength signals from `buildConversationRetrievalSignals`, then `toMemoryResult` (`chat-handlers.ts:1122-1144`) turns the assembled block into a wire `ConversationMemoryResultWire` (`context.text`, per-memory `inclusionReason`/`sensitivity`/`confidence`/`status`). That text is not appended ad hoc — it is placed into the **`working-memory`** lane of the shared 8-lane context budget (`ContextLaneId`, `packages/keiko-contracts/src/context-engineering.ts:37-56`; lane allocation in `packages/keiko-server/src/chat-prompt-budget.ts:148-236`), alongside a sibling `compaction-context` lane. Under budget pressure, memory and compaction are dropped **before** the document lane (`chat-prompt-budget.ts:311-314`). Only scoped excerpts + provenance metadata cross into the model call, never a full vault dump (`docs/conversation-center-privacy.md:19-20`).

Resurfacing (ADR-0172): `buildChatCompactionResurfacingContext` (`chat-compaction-resurfacing.ts:54`) re-injects **persisted** compaction context (not memory) into later turns of the same chat, bounded to 3 records / 8 items-per-section / 220 chars-per-line, after the shared sanitizer filters (`stripUnsafeFormatChars`, NFKC, pseudo-role-marker stripping). `enrichChatCompactionWithModelSummary` (`chat-compaction-model-summary.ts:140`) is a second, optional model-gateway call that produces a rolling continuity summary — the ADR explicitly flags this as the first time compaction (previously purely deterministic) crosses a model boundary.

Voice: the realtime mid-session `recall_keiko_memory` tool (ADR-0116) is **superseded** — its status line states plainly that realtime no longer receives memory instructions or invokes a memory tool, and that final transcripts enter canonical chat, whose existing MemoriaViva path owns retrieval and capture (`docs/adr/ADR-0116-realtime-voice-live-memory-recall.md:3-4`). This is a directly relevant precedent: a tool-driven, model-invoked mid-session recall was built, then retired in favor of the ordinary per-turn retrieval pipeline once transcripts land in chat. `voice-recap.ts` is a second, currently **DORMANT** capture path (`packages/keiko-server/src/voice-recap.ts:1-27`: no current UI caller, deliberately retained, do not remove without a new ADR) that reuses `extractCandidatesFromUserText` unchanged rather than inventing a voice-specific extractor.

Trust-boundary crossings into a model (ADR-0120) are the exception, not the default, and are gated by an explicit default-off env flag plus their own ADR triage — mode-gating (ADR-0146) and model-boundary-gating (ADR-0120) are two independent, composable controls, not one.

### 9.4 Coding Workbench touchpoints today

A repository-wide search of `packages/keiko-server/src/coding-runtime/**/*.ts` (production files, excluding tests) for "memory" returns only in-process RAM usage (`InMemoryRuntimeCapabilityStore`, `InMemoryPendingResearchApprovals`, etc.) — **zero** references to MemoriaViva, `keiko-memory-*`, or memory capture/recall. The coding runtime does not write to or read from MemoriaViva today.

Project instructions for the coding agent are a **fixed, hardcoded system prompt only** — `OPENCODE_GOVERNED_SYSTEM_PROMPT` (`packages/keiko-server/src/coding-runtime/opencodeLaunchProfile.ts:27-38`), injected via `agent.build.prompt` (`opencodeLaunchProfile.ts:94`). The launch profile explicitly disables the bridge engine's own project-level config/instruction-file loading (`opencodeLaunchProfile.ts:71`). The target repository's own `AGENTS.md`/`CLAUDE.md` is therefore **not** auto-loaded into the coding agent's context; the model can only see it if it explicitly reads it as a file via `keiko_workspace_read`.

`AGENTS.md`/`CLAUDE.md` do appear elsewhere, but for a different subsystem: the grounded workspace-search / repo-Q&A ranker treats them as high-priority "repository overview" files — `REPOSITORY_OVERVIEW_FILENAMES` (`packages/keiko-workflows/src/ranking/rank.ts:63-71`) and `OVERVIEW_FILENAMES` (`packages/keiko-workspace/src/repoSearchPolicy.ts:127-128`) both list them. This is a ranking signal for the grounded-answer path, not a project-memory feature for the coding agent.

The nearest thing to "sub-agent" today is `code-task-auxiliary.ts`'s one-layer, read-only `child-agent` capability (`packages/keiko-contracts/src/code-task-auxiliary.ts:1-11,49-52`): outcomes are strictly content-free (ids, digests, counts, bounded reason codes — never raw pages, prompts, child scratch, tool bodies, or secrets). There is no path from a child-agent, skill, or MCP result into a durable `MemoryRecord` today, and no such tool exists in the current `keiko_*` registry.

### 9.6 Constraints the roadmap must respect

- **Dependency-cruiser leaf rule** (`.dependency-cruiser.cjs:386-561`, rules `3f`-`3j`): each of `keiko-memory-capture/consolidation/governance/retrieval/vault` may depend only on `keiko-contracts` + `keiko-security`, and not on each other. `arch:check:negative` pins `EXPECTED_RULES=19` for this cluster — adding a coding-engine-facing memory feature must not add a sideways edge between memory packages.
- **Server-only combiner rule** (`.dependency-cruiser.cjs:663-690`, rule `6a`): `keiko-server` is the only package allowed to hold both a `keiko-memory-*` package and `keiko-model-gateway` (or, by the same logic, coding-runtime) at once. Any engine↔memory feature is composed there.
- **Harness cannot reach `keiko-workflows`** (`.dependency-cruiser.cjs:597-624`, rule `4a`) — see 9.5(e). This directly qualifies any wave-3-style phrasing that assumes "harness consumes `keiko-workflows` context-budget lanes": as worded it is not buildable against the current graph without either moving allocator logic or composing it one layer up in `keiko-server`.
- **Local-knowledge is not leaf-restricted the same way**: `keiko-local-knowledge` may depend on `model-gateway` directly (rule `3e`) — it is the shared ANN substrate (ADR-0164), not a memory-content package, and should stay the one vector-index service.
- **Pure-engine invariant**: `runConsolidation`/`detectConflicts` are synchronous, zero-IO, and byte-identical for the same input (`keiko-memory-consolidation/src/consolidate.ts:1-13`; ADR-0120 context). No roadmap wave may make the consolidation/governance engines async or IO-bearing to serve the coding engine.
- **Env gates already established**: `KEIKO_MEMORY_DIR`, `KEIKO_MEMORY_KEY`, `KEIKO_MEMORY_AUTO_MAINTAIN`, `KEIKO_MEMORY_AUTO_LINK`, `KEIKO_MEMORY_FUSION`, `KEIKO_MEMORY_CONFLICT_ADVISORY` (default off — the model-boundary-crossing gate), `KEIKO_MEMORY_RETENTION_*`, `KEIKO_MEMORY_SALIENCE_MODEL_ID`, `KEIKO_MEMORY_SEMANTICIZATION`, `KEIKO_MEMORY_EMBEDDING_CALIBRATION` — a coding-engine memory feature should extend this table, not invent a `KEIKO_CODING_MEMORY_*` parallel namespace.
- **New trust-boundary crossings need their own ADR-0120-style triage**, per AGENTS.md §7/§12 — this applies directly to (d) and (f)/(g).
- **"No duplicate memory implementation"** is already a closed finding, not just a principle: `docs/memory-verification-matrix.md:131` records that a former standalone memory-viewer route was deleted (#2894, KEIKO-0129) specifically to prevent a second memory surface, and that the desktop Twin panel carries regression coverage ensuring it does not expose a separate localStorage-backed memory store. AGENTS.md §5 and `docs/README.md:86` (memory-* package row: "Must not own: unscoped memory use, plaintext secret storage") are the standing rules this precedent enforces.
- **Privacy contract**: `docs/conversation-center-privacy.md:19-20` — a model call receives only scoped excerpts + provenance metadata, never a vault dump; a coding-engine recall tool must honor the same shape.

### 9.7 Risks of a parallel world

- **A "durable, encrypted, content-bearing session store" risks becoming a second chat-session system** if built without reference to `chats`/`chat_messages` (ADR-0114) and the vault's sealed-column technique (ADR-0035). Single owner: `keiko-server/src/store` for the schema/migration shape, `keiko-security` secretbox for the cipher — not a bespoke encrypted store bolted onto `coding-runtime`.
- **A resume mechanism could silently overload `coding_runtime_snapshots`** into carrying transcript content, defeating the deliberate content-free design from issue #2256 (`store/schema.ts:294-296`). Single owner: the snapshot table stays authority/lifecycle-only; a new table (9.5a) owns content; resume composes both.
- **A "plan artifact" risks becoming a second plan/context substrate** parallel to the already-shared `active-plan` context lane (`contracts/context-engineering.ts:40`) that `keiko-workflows` already allocates budget for. Single owner: the existing `ContextLaneId` union and its allocator (relocated or composed per 9.6), not a new plan-storage format.
- **A "skills registration API" risks duplicating `skillCatalog.ts`'s** server-owned, content-free, closed-category registry with a second, looser catalog. Single owner: extend `skillCatalog.ts`'s categories/entries, don't add a sibling registry.
- **An MCP client risks inventing a second provenance/evidence shape** for tool results instead of reusing the closed, content-free outcome contract `code-task-auxiliary.ts` already established for research/skill/child-agent. Single owner: one `AuxiliaryCapabilityPortV1`-style contract extended with an `mcp` capability, not a parallel MCP-specific result type.
- **A future model-facing memory-recall tool risks re-introducing the exact shape ADR-0116 retired** (a model-invoked mid-session recall tool) without the lesson that motivated its retirement — routing through the ordinary per-turn `retrieveMemoryContext` pipeline once content lands in a durable turn proved simpler than a bespoke tool. Single owner: `keiko-memory-retrieval`'s existing entry point, invoked the same way chat already invokes it.
- **Project/repository memory for the coding agent (9.5c) is absent from every wave in the roadmap skeleton** — a real gap, not a duplication risk in the current draft, but exactly the kind of gap that gets filled by a bespoke "coding-agent memory" store if not explicitly routed through MemoriaViva's existing `project`/`workspace` scope and ADR-0146 mode gate. Single owner: `keiko-memory-capture` + `MemoryScope.project`, added explicitly to a persistence wave.
- **Evidence for the coding engine's own activity (tool cards, usage, plan) risks a bespoke redaction routine** instead of reusing the `redactString`/body-free-by-hard-invariant pattern already proven in `memory-diagnostics.ts:1-22` and `memory-audit-handler.ts`. Single owner: the existing evidence/audit redaction helpers in `keiko-server`, extended, not re-implemented per feature.

## 11. Facts the roadmap must respect

- **`keiko-memory-capture`/`consolidation`/`governance`/`retrieval`/`vault` are leaf-restricted.** Dependency-cruiser rules `adr-0019-direction-3f`..`3j` (`.dependency-cruiser.cjs:386-561`) let each depend only on `keiko-contracts` + `keiko-security`, never on each other; `arch:check:negative` pins `EXPECTED_RULES=19` for this cluster. Any coding-engine/memory feature must not add a sideways edge here (9.6).
- **`keiko-harness` cannot import `keiko-workflows`.** Dependency-cruiser rule `4a` (`.dependency-cruiser.cjs:597-624`) blocks the edge that would let the harness directly consume the 8-lane context-budget allocator; composition must happen in `keiko-server` and be handed down through `keiko-harness/src/ports.ts` (S7).
- **`keiko-server` is the only combiner of memory and model-gateway (or coding-runtime).** Rule `6a` (`.dependency-cruiser.cjs:663-690`) — every engine↔memory feature (S6) is composed there, never inside a leaf package.
- **"One active run per BFF" is one precisely-located guard clause**, not a diffuse constraint: `if (!parsed.ok || this.activeRunId) return this.fail(...)` in `startFresh` (`codingRuntimeOrchestrator.ts:787-788`), reloaded from the durable snapshot on construction. Lifting it for parallel runs is bounded (5.8, 8.1 Decision 7 rows).
- **`coding_runtime_snapshots` is content-free by deliberate design** (issue #2256, `store/schema.ts:294-296`): only enums, digests, and bounded counters may ever land in this table. A resume feature must not add body columns to it — content belongs in a new, separate table (9.7).
- **`packages/keiko-ui/**/globals.css` is behind a byte-exact SHA-256 visual-proof gate** (`globals.css.test.ts:113`, AGENTS.md §9, #1300). Any Workbench styling change must use component-scoped classes (`.cmp-*`) or a CSS module, never an edit to `globals.css` itself (4.8).
- **`packages/keiko-ui/eslint-suppressions.json` is a shrink-only register** (AGENTS.md §6) already carrying 12 Coding Workbench entries. A roadmap change to those files may not add new suppressed violations, and a violation removed must be pruned from the register in the same change.
- **New or removed public exports drift `check:package-surface`.** Any contracts-level enum/type change (Section 6's removal plan, a new `keiko_*` tool, a new connector scope) must run `npm run check:package-surface:assembled` **last**, after `npm test`, since its own prune step deletes native-optional dependencies from the live `node_modules` (AGENTS.md §9).
- **AGENTS.md §8 makes logging part of every change.** Every roadmap child that touches product runtime behaviour must name the `op` values it adds to the generated catalog, thread `correlationId`, and carry a test asserting the emitted lines, so `keiko support analyze` can reconstruct the run (S9).
- **A model-invoked mid-session memory-recall tool was already built and retired once.** ADR-0116 states plainly that realtime voice no longer invokes a memory tool mid-session; ordinary per-turn `retrieveMemoryContext` once transcripts land in chat proved simpler. A future `keiko_*` recall tool (9.5d) must address why that shape was retired before repeating it.
- **Every new trust-boundary crossing into a model needs its own ADR-level triage**, not just a code review — ADR-0120's `KEIKO_MEMORY_CONFLICT_ADVISORY` (default off) is the only precedent for MemoriaViva content crossing the model-gateway boundary today, and it required exactly this (9.1, 9.6).

A rebuilt delivery path must mint authority server-side from the live, active workspace binding, exactly like every other coding-runtime route (5.1, 6.1 item 1).
- **Every governed tool call is re-authorized against the live envelope**, never a cached launch-time decision (`codingToolAuthorityPort.ts:71-99`). A replacement engine loop must preserve this or the 2.1 trust model regresses.
- **Sandbox network isolation is opt-in, not the default posture.** `DEFAULT_SANDBOX_POLICY` is `network:"inherit"` (`keiko-contracts/src/tools.ts:86-96`); a caller must explicitly request `network:"none"` to get `keiko-sandbox`'s fail-closed wrapping (3.3). - **The three-mode authority matrix is pinned monotonic by a regression test.** `coding-workbench.test.ts:292-307` asserts `strictestCodingWorkbenchPolicyEffect(lower, higher) === lower` for every adjacent mode pair, scope, and risk — a new action-kind or resource-scope value must satisfy this invariant, not just its own new test (5.2).

- **`gates:sonar` is mandatory before every pull request** and runs a real analyzer no locally-run ESLint plugin covers (AGENTS.md §3) — every roadmap child, however small, needs this run before it can be considered gate-clean, not only `typecheck`/`lint`/`test`.
- **GitHub Actions are pinned to full 40-hex commit SHAs with a version comment**, and any new long-lived integration branch must be added in three separate places in `ci.yml` — the `push:` trigger list, the `pull_request:` trigger list, and the protected-branch-gate allowlist (AGENTS.md §9, §11) — a roadmap that introduces its own working branch convention must not skip the third.
- **`npm run provision:usearch` is a real prerequisite, not optional**, for the two Knowledge-M2 proof suites the memory/retrieval reuse in Section 9 depends on (AGENTS.md §2); a fresh checkout that skips it will show a false red on ANN-backed retrieval work.
