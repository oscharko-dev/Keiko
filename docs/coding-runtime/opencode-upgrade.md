# Upgrading the pinned OpenCode runtime

Keiko runs the original OpenCode service per Coding Workbench run (ADR-0137 D10). This page names
the files and commands an upgrade changes. It also covers what to do when the producer breaks a
contract, and which evidence proves that the upgrade kept every native capability (#3908, #4271).

## 1. What an upgrade changes

Every version identity reads from one file, `packages/keiko-contracts/src/opencode-runtime-pins.json`.
`opencodeRuntimeVersions.test.ts` refuses a quoted version in production code, a test fixture path
naming the current pin, and the words `pinned <version>` in any source, so a comment recording what
one version did may name it. Two files state versions on purpose:
`npmLaneRuntimeApprovals.ts` names what was published, and `opencodePersistenceContract.ts` binds
each version's database schema.

| Input                                                             | What changes                                                                                                                                                                                                                                                                                                        |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `opencode-runtime-pins.json`                                      | A new pin goes first: version, tag, commit, raw schema digest, projected protocol-surface digest. The report prints the entry. An upgrade is its own pull request and carries only the rows of this table. Hardening, fixes and
features found while upgrading are recorded in the upgrade issue and delivered in a separate pull
request after the upgrade merged (owner decision, 2026-11-06), so the upgrade's own size stays
reviewable.

## 2. Commands, in order

Run them in a clean checkout of the branch that carries the bump.

1. Read what the upgrade changes before touching anything. The report writes nothing and needs a
   prior `npm run build:packages`:

   ```bash
   node scripts/opencode-upgrade-report.mjs --to <version>
   ```

   It prints the pin entry, the upstream breaking changes, the admitted endpoints that went missing
   or changed, every operation and setting that needs a disposition, and the new migrations, tools
   and plugins. A missing admitted endpoint or a breaking change that reaches Keiko is section 3
   work; plan it before you continue. Re-check for a newer upstream release and freeze the target.

2. Put the printed entry first in `opencode-runtime-pins.json`, then run
   `npm run portable:approve-runtimes -- --opencode-version <version>` and
   `npm run check:portable-approvals`.
3. Stage the payload: `npm run dev:coding-runtime:stage` for the dev lane, or
   `npm run portable:prepare-sidecars` for the release lanes.
4. Write the fixtures from the real binary. Run the real-binary suites with
   `KEIKO_OPENCODE_REAL_BINARY` and `KEIKO_OPENCODE_REAL_RESOURCE_ROOT` set to the staged payload and
   the write flags from section 1 set; each fixture's diff against its predecessor is the drift.
   `opencodeRuntime.real.test.ts` and the `[functional-only]` backend suite take the parent of the
   payload as `KEIKO_OPENCODE_REAL_RESOURCE_ROOT`.
5. Run `opencodeServiceInventory.test.ts`. It refuses an operation without a disposition, a stale
   disposition and an admitted set that differs from the pinned surface.
   `diffOpenCodeServiceOperations` lists the added, removed, moved and breaking operations between
   the two fixtures, and `diffOpenCodeConfigurationPaths` the added and removed setting paths. The
   test refuses a setting or a built-in plugin without a disposition and a `keiko-set` table that
   differs from what the native profile composes. Give every real capability change an owner in the
   tables, then regenerate the documentation sections with
   `KEIKO_WRITE_OPENCODE_SERVICE_INVENTORY_DOC=1`.
6. Classify every table of the new persistence schema in `opencodePersistenceContract.ts`, and add
   a retention check when a new table can hold state a retained copy must not carry.
7. Run every `opencode*.real.test.ts` suite again without the write flags. They cover the native
   tools, boundaries, revert, prompt inputs, retention and offline search. Set
   `KEIKO_OPENCODE_PREVIOUS_REAL_BINARY` to the previous runtime, which an installed npm runtime
   package carries, so `opencodeServiceInventory.real.test.ts` proves it still starts under the new
   profile.
8. Run the ordinary gates of AGENTS.md section 3: `typecheck`, `lint`, `format:check`, `test`,
   `gates:sonar`. `check:package-surface:assembled` when a contracts export changed. Commit, then
   measure the performance evidence above, last. `check:activity-log` includes the tool-catalog
   performance check, so it passes only after that measurement.
9. Prove the upgrade on the normal user path with a model, before and after: a Coding Workbench run
   through the UI on a clean state directory.

A digest-only upgrade stops here. An upgrade with a changed contract also changes its owning adapter
(section 3), and any change to product runtime behaviour ships its own Activity Log evidence. No
upgrade reaches a product surface outside the coding runtime.

## 3. When the producer breaks a contract

Breaking changes stay inside the owning adapter. Each module below owns one upstream contract:

- `opencodeV2HttpClient.ts`: the HTTP API and its bounded parsing.
- `opencodeV2History.ts` and `opencodeSafeActivity.ts`: message, part and event shapes.
- `opencodeLaunchProfile.ts`: configuration keys and the server-owned binding.
- `opencodeNativePolicyPlugin.ts` and `opencodeRuntimeAdapter.ts`: generated plugins and hooks.
- `opencodeNativeTools.ts`: the tool registry and permission actions.

Chat, repository search, the manual Editor and the governed tool catalog never import from them.

A schema the adapter does not know stays unadmitted. Never make it executable, and never widen the
mode policy to make an upgrade pass: the failure-closed decoders and the protocol-surface digest
refuse it. Record the change in the affected ADR-0137 section and in the parity matrix
(`docs/qa/opencode-capability-parity.md`), with its proof.

## 4. Rollback and persisted state

Rolling back means reverting the bump commits. The previous pin, its fixtures and the
`portable-runtime-approvals.json` entries come back with them, and nothing needs migrating:

- The runtime's own state, `OPENCODE_DB`, its snapshots and the run's private configuration, lives
  under the run's private state root and is removed when the run is disposed (`disposeRun` in
  `opencodeRuntimeComposition.ts`).
- A native run that settled normally may leave one retained copy of its session database for the
  next run of the same Coding History task (#3904, `opencodeSessionRetention.ts`). The copy is
  compacted and audited first: it must hold exactly that one session and no saved grant, credential,
  queued input or staged undo. It lives in the server's state directory, never in a workspace. It
  is bound to the task, a digest of the workspace identity, the pinned runtime version and the
  model window it was built under, and bounded in size, number and age (14 days).
- A later run checks the entry out only if every binding still matches. After an upgrade or a
  rollback the version differs, so the entry is refused (`version-changed`) and removed. A changed
  workspace (`workspace-changed`), an expired entry, a failed integrity or audit check and an
  unknown schema are refused and removed the same way. A smaller model window (`window-shrunk`)
  is refused but kept, since a larger window can still use it. One OpenCode version therefore
  never reads a session database another version wrote.
- A refused or missing entry is never an error for the task: the run starts a fresh native session
  with the task's Coding History as context, and `coding-runtime.session-continuity` records the
  closed reason.
- Tasks, Coding History, selected models, workspace bindings and credentials are Keiko's own,
  version-independent state. An upgrade or a rollback leaves them as they are.
- A runtime that presents an unpinned version, or a digest that differs from its pin, is refused
  before any run starts. The status is `payload-unapproved`, or `payload-tampered` for a changed
  payload.

## 5. Evidence that native capabilities were kept

- The service inventory diff, for example 2.1.4 to 2.2.5: 149 to 169 operations with every admitted
  endpoint kept, 16 configuration settings added, and five built-in plugins added and three removed.
- The real-binary suites above, on the new pin.
- The parity matrix rows (T01–T22, S01–S19, C01–C08), each re-verified, or marked with what was not
  re-run.
- The performance evidence measured on the declared reference environment.

The owner's release steps then follow: publishing the npm runtime packages, attesting both portable
variants, and updating the npm-lane approvals. They happen only after the exact head passes its
security, license, platform and package checks (#3898). Until the root package selects runtime
packages built from the new pin, `release:publish` refuses a product release: each reviewed entry in
`docs/release/coding-runtime-npm-packages.json` records the OpenCode it carries (`opencodeVersion`),
and a selected package must carry the version `portable-runtime-approvals.json` approves (#4271).
