# Upgrading the pinned OpenCode runtime

Keiko runs the original OpenCode service per Coding Workbench run (ADR-0137 D10). This page names
the files and commands a compatible upgrade changes. It also covers what to do when the producer
breaks a contract, and which evidence proves that the upgrade kept every native capability (#3908).
The 2.0.10 to 2.1.4 upgrade in PR #4064 followed this procedure, starting with commit `1cce5e001`.

## 1. What a compatible upgrade changes

All version-specific identities live behind one boundary. Nothing else in Keiko restates a version
or a digest.

| Input                                                                                                                    | What changes                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scripts/portable-runtime-approvals.mjs`, `APPROVED_OPENCODE_VERSION` in `scripts/update-portable-runtime-approvals.mjs` | The new release version, tag and upstream commit.                                                                                                                                             |
| `portable-runtime-approvals.json`                                                                                        | Regenerated by `npm run portable:approve-runtimes`: archive, executable-tree, SBOM, license and protocol-schema digests per platform. Never edited by hand.                                   |
| `packages/keiko-server/src/coding-runtime/opencodeRuntimeVersions.ts`                                                    | A new pin (version, tag, commit, raw schema digest, projected protocol-surface digest) goes first; the previous pin stays while published npm runtime packages still carry it.                |
| `opencodeProtocolSurface.opencode-<version>.fixture.json`                                                                | The projection of the new `/openapi.json` onto the admitted operations; its digest is the pin's `protocolSurfaceSha256`.                                                                      |
| `opencodeNativeTools.opencode-<version>.fixture.json`                                                                    | The producer's tool registry and permission actions, captured from `ctx.tool.list()` and the permission hook. `opencodeNativeQualification.real.test.ts` pins every id against it.            |
| `opencodeServiceInventory.opencode-<version>.fixture.json`                                                               | Every operation, CLI command and configuration setting path of the new producer. Write it with `KEIKO_WRITE_OPENCODE_SERVICE_INVENTORY_FIXTURE=1` on `opencodeServiceInventory.real.test.ts`. |
| `npmLaneRuntimeApprovals.ts`                                                                                             | Only after the owner publishes runtime packages built from the new pin.                                                                                                                       |
| Performance evidence                                                                                                     | The tool-catalog evidence is rebound (`npm run perf:evidence:regen:tool-catalog -- --rebind-case-identity`); the coding-runtime calibration is re-measured (`docs/qa/perf-evidence.md`).      |

## 2. Commands, in order

Run them in a clean checkout of the branch that carries the bump.

1. Update the version, tag and commit in the two scripts named above, then run
   `npm run portable:approve-runtimes` and `npm run check:portable-approvals`.
2. Stage the payload: `npm run dev:coding-runtime:stage` for the dev lane, or
   `npm run portable:prepare-sidecars` for the release lanes.
3. Add the new pin to `opencodeRuntimeVersions.ts`. Then run the real-binary suites with
   `KEIKO_OPENCODE_REAL_BINARY` and `KEIKO_OPENCODE_REAL_RESOURCE_ROOT` set to the staged payload:
   - `opencodeServiceInventory.real.test.ts`, which compares the live operation, CLI and
     configuration-setting inventory with the committed fixture. With the write flag it rewrites
     the fixture; the diff is the drift.
   - `opencodeNativeQualification.real.test.ts`, `opencodeNativeProjectBoundary.real.test.ts`,
     `opencodeNativeRevert.real.test.ts`, `opencodeNativePromptInputs.real.test.ts` and
     `opencodeRipgrep.real.test.ts`, which cover the native tools, boundaries, revert, prompt inputs
     and offline search.
4. Run `opencodeServiceInventory.test.ts`. It refuses an operation without a disposition, a stale
   disposition and an admitted set that differs from the pinned surface.
   `diffOpenCodeServiceOperations` lists the added, removed, moved and breaking operations between
   the two fixtures, and `diffOpenCodeConfigurationPaths` the added and removed setting paths. The
   test refuses a setting without a disposition and a `keiko-set` table that differs from what the
   native profile composes. Give every real capability change an owner in the tables, then
   regenerate the documentation sections with `KEIKO_WRITE_OPENCODE_SERVICE_INVENTORY_DOC=1`.
5. Run the ordinary gates of AGENTS.md section 3: `typecheck`, `lint`, `format:check`, `test`,
   `check:activity-log`, `gates:sonar`. Then the performance evidence above, last.

An ordinary compatible upgrade stops here. It changes no adapter code, and no product surface
outside the coding runtime.

## 3. When the producer breaks a contract

Breaking changes stay inside the owning adapter. Each module below owns one upstream contract:

- `opencodeV2HttpClient.ts`: the HTTP API and its bounded parsing.
- `opencodeV2History.ts` and `opencodeSafeActivity.ts`: message, part and event shapes.
- `opencodeLaunchProfile.ts`: configuration keys and the server-owned binding.
- `opencodeNativePolicyPlugin.ts` and `opencodeRuntimeAdapter.ts`: generated plugins and hooks.
- `opencodeNativeTools.ts`: the tool registry and permission actions.

Chat, repository search, the manual Editor and the governed tool catalog never import from them.

A schema the adapter does not know stays unadmitted. Never make it executable, and never widen the
mode policy to make an upgrade pass: the failure-closed decoders and the protocol-surface digest
refuse it. Record the change in the affected ADR-0137 section and in the parity matrix
(`docs/qa/opencode-capability-parity.md`), with its proof.

## 4. Rollback and persisted state

Rolling back means reverting the bump commits. The previous pin, its fixtures and the
`portable-runtime-approvals.json` entries come back with them, and nothing needs migrating:

- The runtime's own state, `OPENCODE_DB`, its snapshots and the run's private configuration, lives
  under the run's private state root and is removed when the run is disposed (`disposeRun` in
  `opencodeRuntimeComposition.ts`).
- A native run that settled normally may leave one retained copy of its session database for the
  next run of the same Coding History task (#3904, `opencodeSessionRetention.ts`). The copy is
  compacted and audited first: it must hold exactly that one session and no saved grant, credential,
  queued input or staged undo. It lives in the server's state directory, never in a workspace. It
  is bound to the task, a digest of the workspace identity, the pinned runtime version and the
  model window it was built under, and bounded in size, number and age (14 days).
- A later run checks the entry out only if every binding still matches. After an upgrade or a
  rollback the version differs, so the entry is refused (`version-changed`) and removed. A changed
  workspace (`workspace-changed`), an expired entry, a failed integrity or audit check and an
  unknown schema are refused and removed the same way. A smaller model window (`window-shrunk`)
  is refused but kept, since a larger window can still use it. One OpenCode version therefore
  never reads a session database another version wrote.
- A refused or missing entry is never an error for the task: the run starts a fresh native session
  with the task's Coding History as context, and `coding-runtime.session-continuity` records the
  closed reason.
- Tasks, Coding History, selected models, workspace bindings and credentials are Keiko's own,
  version-independent state. An upgrade or a rollback leaves them as they are.
- A runtime that presents an unpinned version, or a digest that differs from its pin, is refused
  before any run starts. The status is `payload-unapproved`, or `payload-tampered` for a changed
  payload.

## 5. Evidence that native capabilities were kept

- The service inventory diff, for example 2.0.10 to 2.1.4: 13 operations added, none removed, and
  33 configuration settings added, none removed.
- The real-binary suites above, on the new pin.
- The parity matrix rows (T01–T22, S01–S19, C01–C08), each re-verified, or marked with what was not
  re-run.
- The performance evidence measured on the declared reference environment.

The owner's release steps then follow: publishing the npm runtime packages, attesting both portable
variants, and updating the npm-lane approvals. They happen only after the exact head passes its
security, license, platform and package checks (#3898).
