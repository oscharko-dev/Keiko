## 1. Verification method and its declared limits

Journeys were executed through the real shipped UI on the development start path
(`npm run dev:start`), not through a side path and not through unit tests. API and server
projections were used only as supplementary diagnosis, as §2 of the cluster handoff requires.

### 1.1 Model-gateway substitution — read this before trusting any journey result

Keiko blocks first start on a model-gateway credential (base URL + API token) and the audit host
holds no provider credential. To exercise the product pipeline without any secret, the
model-dependent journeys were driven against a **hermetic loopback stub gateway** — an
OpenAI-compatible loopback responder, dependency-free, no external network, no persistence,
held outside the repository in the session scratchpad. Loopback egress is permitted by default
(`denyLoopback` defaults to false, `packages/keiko-model-gateway/src/egress-policy.ts:232`).

The stub was configured **through the product's own first-run GUI**, so the onboarding, discovery,
persistence and readiness code paths are the real ones.

**What the stub does prove:** the transport, discovery, streaming, history, error, recovery,
readiness-projection and UI paths are real product code and behaved as recorded below.

**What the stub cannot prove, and what therefore remains unaudited:** answer quality, grounding
faithfulness, correct abstention, citation correctness, retrieval ranking, judge behaviour,
`response_format` structured-output support, real dictation and Realtime/Digital-Twin media
negotiation, and any provider-specific capability negotiation. Those require a real gateway
credential and are listed as external blockers in §5.

No real credential was entered at any point. The token used was a deliberately invalid
non-secret placeholder.

## 4. Findings

Severities follow the handoff. Only findings with recorded evidence are listed.

### F-01 · P0 · Coding Workbench renders green readiness over an `unavailable` gateway

**Evidence.** With a reachable, UI-onboarded gateway:

- the server's coding-sidecar gateway profile projection reports status `unavailable` with reason `no-tool-calling`
- Settings → Models reports `tools yes` for both chat models
- Coding Workbench header reports **`Ready to start`** and **`Model source: Keiko Gateway`**

Two server projections disagree about tool-calling for the same model, and the Workbench surfaces
no unavailability at all. A user is invited to bind a workspace and start a coding task against a
gateway its own profile calls unusable. This is the contradiction the handoff classes as P0
("no green readiness display when the functional flow is unusable").

**Declared uncertainty.** The stub advertises function calling via `/model/info`
`model_info.supports_function_calling`. Whether a production gateway also lands on
`no-tool-calling` requires a real credential. The **display** defect is independent of which
projection is correct: the Workbench must not show green while its own gateway profile is
`unavailable`.

**Required action.** Derive the Workbench readiness chip from the same projection that answers
the sidecar gateway profile projection, and reconcile the two tool-calling predicates at the layer
that owns model capability.

### F-02 · P1 · A failed readiness probe never changes the top-level gateway indicator

**Evidence.** With the provider stopped, Settings → Models continues to render
`Gateway connected · 3 models · 2 chat` with a green dot, in the same view where the live probe
reports `Not verified`. Chat concurrently fails with `GATEWAY_TRANSPORT`.

The functional surface and the live probe both tell the truth, so no user is misled at the point
of use — this is why it is P1 and not P0. But the green summary is a readiness display that
survives an unusable gateway.

**Required action.** Make the summary reflect the last probe outcome, or relabel it as
_configured_ rather than _connected_.

### F-03 · P0 (release-blocking, repository configuration) · `release/0.2` protection requires two contexts no workflow can emit

**Evidence.** `release/0.2` required contexts are
`["ci","actionlint","Verify pinned action SHAs","Analyze (actions)","Analyze (javascript-typescript)","Build, scan, SBOM, smoke","Review dependency diff (dev/main)","ui"]`.
Since ADR-0159 `actionlint` and `Verify pinned action SHAs` are **step** names inside the single
`workflow hygiene` job (`.github/workflows/workflow-hygiene.yml:86`); no workflow emits them as
check contexts. Any PR into `release/0.2` therefore waits forever on two checks that can never
report.

**Required action.** When `release/0.3` is created, set its required contexts to the names
workflows actually emit (replace the two stale contexts with `workflow hygiene`). Do not clone
`release/0.2`'s protection. Needs repository admin — see §5.

### F-04 · P0 · The release-impact catalog has no `0.3.0` entry

**Evidence.** `portable:stage` and `check:release-impact` fail closed the moment the root version
becomes `0.3.0` without a reviewed catalog entry. A pre-existing entry additionally uses a
non-GitHub `approvalReference` that `check:release-impact:publish` rejects.

**Required action.** Append a reviewed `0.3.0` entry (append-only; the `0.2.15` rows must not be
edited) and correct the rejected `approvalReference` before the publish gate runs.

### F-05 · P1 · 12 of 45 window types have no reachable entry point; `TYPE_ORDER` is not the shipped palette

**Evidence.** 45 declared types, 25 in `TYPE_ORDER`, 6 in the shipped palette. The tests that
guard "the default window order" assert against `TYPE_ORDER`, which the shipped palette does not
use, and several e2e suites seed unreachable windows directly into `localStorage`, so release
gates can stay green over UI no user can reach. `governedPullRequest` and `governedMerge` exist
both as unreachable window types and as inline panes of the reachable Git window.

**Required action.** Per handoff §3, every visible clickable function must work, be removed from
the shipped UI before 0.3.0, or carry an explicit controller-approved release decision. Decide per
type and record the decision.

### F-06 · P1 · Text / dictation / Realtime parity is not established

**Evidence (static).** Realtime spoken turns drop pending attachments and extracted document
context; a spoken turn cannot be stopped and new speech hard-cancels the in-flight answer,
stranding the user message; voice resolves the target model differently from the typed path, so a
spoken turn can be admitted where a typed turn is blocked.

**Not reproduced through the UI** — dictation and Realtime need a real media-capable deployment.
Handoff §14.2 makes unproven voice/Realtime parity a No-Go on its own.

### F-07 · Strengthened during this audit · Release-contract drift pin would have gone green over a real drift

`scripts/__tests__/release-portable-assets-workflow.test.mjs:700` mutated the literal
`"release/0.2"`. After migrating the workflows the literal no longer occurs, `String.replace`
returns the input unchanged, and the pin asserts drift detection against an unmutated file —
green over an undetected contract drift. Fixed by deriving the value from the production reader
(`envValue`), per `AGENTS.md` §7. Proven: passes pre-migration, passes post-migration, and
**fails** when the two workflows genuinely disagree. The pin was strengthened, never relaxed.

## 7. Version bump to 0.3.0 — NOT performed

Handoff §10 permits the bump only after a green functional baseline. That baseline cannot be
certified here (B-1, B-2, B-3, B-4). The surface is mapped and ready:

26 `package.json` `version` fields (root + 25 workspaces) · 124 internal
`@oscharko-dev/keiko-*` dependency pins in lockstep · 14 exported `KEIKO_*_VERSION` constants
(`KEIKO_PRODUCT_VERSION` is what the UI, CLI and health surface read) · 17 hardcoded `0.2.15`
literals in co-located tests, two of them in `it()` titles · 151 `package-lock.json` version lines
(regenerate, never hand-edit) · a reviewed `0.3.0` release-impact entry (F-04) · the macOS
system-extension `Info.plist` version fixture, which restates the producer and will fail · a
hardcoded product version reported to the Codex sidecar, currently ungated.

Note: bumping the minor resets the SonarCloud leak period, so expect a materially larger new-code
set on the first 0.3.0 PR.

Binding created the workspace at `<repoRoot>/.keiko/dev/ui/task-workspaces/repo_…/ws_…`;
`packages/keiko-workspace/src/ignore.ts` `DEFAULT_DENY_PATTERNS` (correctly) denies `.keiko` —

`state: unavailable` with the content-free reason `unknown` and every Files/Git/diff surface for the product's own managed workspace is
denied ("The requested path is excluded from the read surface"). The deny list must NOT be
weakened (`.keiko/dev/ui/credentials` is a sibling); the class fix is relocating managed task
workspaces outside every deny-listed segment, or a server-side allow for exactly the
lifecycle-registered roots. `reason:"unknown"` is additionally poor diagnostics.

**F-09a · P0 · Silent 403 on "Start coding run".**
`startFresh` fails with `authority-resolution-failed`

**F-09b · P1 · Client-persisted binding outlives server authority.**

**F-10 · P0 (publish leg) · The npm-publish approval gate is structurally unsatisfiable under
ADR-0135.** `check:release-impact:publish` requires `approvalReference` of the form
`github-pr-review:<owner>/<repo>#<pr>#<review>` pointing at an `APPROVED` PR review by a

**F-11 · P1 · Model-assisted memory salience fails on every turn against the real gateway.**

### 10.5.3 Corrections to this document's own earlier numbers
