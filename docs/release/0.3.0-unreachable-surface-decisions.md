# 0.3.0 Unreachable Window Surface — Controller Decision Matrix (audit finding F-05)

Status: analysis only, produced for the 0.3.0 release audit on 2026-07-30. Every recommendation in
this document is **PENDING CONTROLLER APPROVAL** — no window type, widget, or entry point may be
removed, hidden, or wired without an explicit release decision by the controller. This document
changes no code.

Scope: `packages/keiko-ui` window types declared in
`packages/keiko-ui/src/app/components/desktop/windows/WindowsRegistry.ts` and every user-facing or
programmatic spawn seam in the shipped UI. All file references are repo-relative; all line numbers
were verified against the audit worktree at base `origin/dev` (dd210432 lineage).

## 2. Corrections to the audit ground truth

1. **The registry declares 43 window types, not 45** (`WindowsRegistry.ts`; counted
   mechanically: 43 union members). The audit's 45 likely counted `editor-settings`, which is not a
   `WindowType` — it is a Quick Access pseudo-command that toggles the `settings` singleton and
   dispatches `OPEN_EDITOR_SETTINGS_EVENT` (`AppShell.tsx:615-626`).
2. **Three suspected-unreachable types are in fact reachable** — `search` (keyboard-only), and
   `problems` / `debug` (editor-command-only). Evidence in the matrix below.
3. **Two formerly missing decisions are implemented pending merge.** The controller accepted the
   `keiko` deletion in #2950 and directed the server-bound `integ` replacement in #3108. PR #3278
   carries both implementations; they become resolved release state only after that PR merges.
4. **Unreachable does not mean inert.** The persistence layer restores any declared `WindowType`
   from `localStorage` (`workspace-persistence.ts:139-141`), so every "unreachable" window renders
   fully if a persisted layout contains it (older build, shared profile, or manual tampering with
   workspace-input data, which AGENTS.md §7 treats as hostile). Conversely, if a type is removed
   from the union, `hasWindowType` silently drops the stale persisted window — removal degrades
   gracefully.

(`widgets/index.tsx:32-170`), so an unreachable surface ships as an async chunk in the static
export plus its registry metadata, descriptor metadata, and i18n strings in the main bundle — dead

## 4. Cross-cutting findings

1. **`TYPE_ORDER` is dead production code with a stale test pinned to it.** The export
   (`WindowsRegistry.ts:1012-1030`) is consumed by no production module — the shipped palette
   sources `QUICK_ACCESS_CARD_TYPES` instead (`AppShell.tsx:1399`), which
   `quickAccessRegistry.ts:44-47` explicitly calls "the known wrong-list trap". Its only consumer
   is `Palette.test.tsx:3-8`, which renders the Palette with `TYPE_ORDER.slice(0, 10)` — a list
   whose members `figmaJson` and `problems` are absent from the shipped palette. Whatever the
   controller decides per type, `TYPE_ORDER` should be deleted or re-pointed at the real list in
   the same change so the test pins the shipped surface (~0.5 d).
2. **Persisted-layout hydration is the only live path to every unreachable surface.**
   `hasWindowType` (`workspace-persistence.ts:139-141`) accepts any declared type from
   `localStorage`; the persistence layer already hardens cfg values (e.g. credential-filename
   scrubbing, `workspace-persistence.ts:184`), and the server-side gates (ADR-0017 loopback CDP,
   ADR-0018 command allowlist, ADR-0070 frozen catalog) remain the trust boundary — so this is a
   robustness/audit-surface issue, not privilege escalation. Removal of a type degrades gracefully:
   stale persisted windows of an unknown type are silently dropped.
3. **Counting for the release note.** 43 declared types, split without overlap:

   | Class                                                                    | Count | Types                                                                                                                                                                                        |
   | ------------------------------------------------------------------------ | ----: | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | Pointer-visible (palette card, rail entry, Quick Access tool, deep link) |    26 | —                                                                                                                                                                                            |
   | Keyboard-only                                                            |     1 | `search`                                                                                                                                                                                     |
   | Editor-command-only                                                      |     2 | `problems`, `debug`                                                                                                                                                                          |
   | Programmatic-by-design (opened by a feature, never listed)               |     4 | `qiRun`, `figmaView`, `figmaJson`, `figmaImage`, `pdfCitationPreview`, `updates` — 6 entries, of which 2 (`figmaJson`, `updates`) are also Quick Access/settings-reachable and counted above |
   | **Unreachable — no entry point at all (direct)**                         | **6** | `runtime`, `terminal`, `review`, `project`, `plugins`, `browser`                                                                                                                             |
   | **Unreachable — transitively, only openable from `runtime`**             | **4** | `commands`, `containerStatus`, `governedPullRequest`, `governedMerge`                                                                                                                        |

   **10 window types are unreachable by any user** (6 direct + 4 transitive). Two of the transitive
   four — `governedPullRequest` and `governedMerge` — are counted here as dead _window wrappers_,
   not dead capabilities: the pull-request and merge capability itself ships as inline panes of the
   reachable Git window, so removing the wrappers would not remove a feature. An earlier revision
   of this document stated "9"; that number was wrong and is corrected here.

## 5. Effort model used above

- **Wire into Quick Access tools** (`QUICK_ACCESS_TOOL_TYPES` entry): ~0.5 day — list entry, en+de
  i18n labels, `commandIdsForEvidence`/registry test updates.
- **Wire as New-window palette card** (`QUICK_ACCESS_CARD_TYPES`): ~0.5-1 day — card list, palette
  a11y pass, dialog config-flow verification.
- **Hide from bundle** (remove type): ~1-2 days per type — union member, `PARTIAL` entry, render
  registration, widget file(s), `descriptor-meta.ts` row, `connectionUtils.ts` compatibility lists,
  test and coverage-baseline churn; stale persisted layouts self-heal (finding 4.2). Removing the
  `runtime` cluster together: ~3-5 days.
- **Leave dark, documented**: zero code, but the surface remains hydratable dead weight and must be
  re-audited each release.
