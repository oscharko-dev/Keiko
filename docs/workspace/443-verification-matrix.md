| Scenario class        | Representative trigger                                                                                                              | Proof / operator interpretation                                                                                                                                | Tests                                                                                                                                                             |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Retryable**         | Lock contention (live advisory lock held by another actor, will expire); transient provisioning failure                             | Caller retries as-is; lock release or retry timeout resolves the condition                                                                                     | `concurrency.test.ts`, `provisioning.test.ts:327–340` (LOCK_CONTENTION code, retryable class)                                                                     |
| **Repairable**        | Pointer drift (worktree moved externally, .git pointer invalid, stale lock TTL expired); partial provisioning                       | Caller routes to repair via reconciliation + strategy selection (recreate-worktree, relink-gitdir, release-lock). Bare retry re-hits the same stale condition. | `repair.test.ts` (all 4 strategies), `reconciliation.test.ts:172–245` (drift markers triggering repair routes)                                                    |
| **Blocked**           | Illegal state transition (e.g. resume paused-paused, activate active-active), missing repository, branch conflict, out-of-root path | Precondition failed; caller must change inputs or environment. Type system enforces legal transitions; state machine rejects mutations.                        | `lifecycle.test.ts:217–241` (illegal transition typed rejection), `provisioning.test.ts:194–261` (precondition gates: missing-repo, branch-conflict, path-escape) |
| **Policy-denied**     | Approval-gated repair (e.g. operator approval required for abandon-and-cleanup); authorization failure                              | Governance gate, not retry. Caller requests/refreshes approval or changes policy. | **Terminal**          | Workspace not found, invalid request, missing repository after authorization, unrecoverable corruption                              | Non-recoverable server fault; out-of-band intervention (e.g. manual data recovery, retry with clean slate).                                                    | `provisioning.test.ts:194–261` (terminal errors: MISSING_REPOSITORY), all service tests (terminal error codes)                                                    |
| **Dirty state**       | Workspace has uncommitted/untracked changes; cleanup or hand-off precondition fails (AC2/SC1)                                       | Health classification: `dirty`. ## Browser evidence boundary

The existing e2e fixture `tests/e2e/task-workspace-binding-446.spec.ts` (Issue #446) drives the real packaged app and proves UI re-targeting with no stale context after active-workspace switch. It uses deterministic route interception (JSON mocks for task-workspace + files endpoints), not live-provider proof. It verifies that the Files surface correctly re-targets the active workspace root and does not leak stale previous-root context across a switch operation.

This is evidence of browser surface correctness (AC5: "The UI makes active task, branch, workspace path, health, dirty state, and lock state visible enough for operators to trust the current context") but NOT evidence of active-pointer derivation or Git mutation execution. Server lifecycle proof comes from the unit, integration, and route suites listed in the lifecycle-path matrix above.
